# Rush: eager и lazy, время и память

Дата: 2026-10-01. Локальный macOS/aarch64, release/bench profile,
`rustc 1.101.0-nightly (c1070d693 2026-09-28)`. Измерена текущая рабочая копия;
это не результат опубликованного релиза. [Полные результаты](benchmarks/rush-memory-2026-10-01.txt).

## Одинаковое вычисление

```rush
range(0, N) | map(x => x * 2) | filter(x => x % 3 == 0)
    | fold(0, (sum, x) => sum + x)
```

В lazy-варианте только `range` заменён на `range_iter`. Оба полностью обходят
источник и возвращают число. Перед измерением результат сверяется с независимым
целочисленным вычислением в Rust: 333666, 3333366666 и 333333666666 соответственно.
Бюджет одинаков: `N * 100 + 100000`; отмена не запрошена.

## Время подготовленной программы

Каждая строка измерена в отдельном процессе: один проверочный запуск, 10 прогревов,
7 измерений по одному выполнению. Таблица показывает медиану; минимумы и максимумы
сохранены в полных результатах. Инициализация runtime входит во время, компиляция
исходника — нет. Порядок: eager, затем lazy, от меньшего N к большему.

| N | Eager, мс | Lazy, мс |
| ---: | ---: | ---: |
| 1 000 | 0.853 | 0.885 |
| 100 000 | 86.783 | 88.777 |
| 1 000 000 | 876.867 | 896.242 |

В этом сценарии lazy не ускоряет полный обход. Разница порядка нескольких процентов
не является устойчивой оценкой без повторов с чередованием порядка и контроля нагрузки.

## Живые выделения памяти

Отдельный benchmark `memory` оборачивает системный Rust-аллокатор счётчиком размеров
из `Layout`. Он отслеживает alloc, alloc_zeroed, realloc и dealloc. Сначала проверяет
счётчик на создании, расширении и удалении вектора. Программа компилируется до замера;
за baseline берутся уже живые выделения. Счётчик не используется в benchmark времени.

| N | Пик дополнительных байтов eager | Пик дополнительных байтов lazy | Число выделений eager / lazy |
| ---: | ---: | ---: | ---: |
| 1 000 | 97 304 | 24 128 | 8 739 / 8 713 |
| 100 000 | 10 501 144 | 24 128 | 866 760 / 866 713 |
| 1 000 000 | 83 901 464 | 24 128 | 8 666 769 / 8 666 713 |

Все три повтора каждой строки дали одинаковые значения. После удаления результата
число живых байтов вернулось к baseline во всех 18 исполнениях; это проверяется assert.
Пик lazy остаётся постоянным для этой программы с числовыми элементами. Замыкания,
вложенные значения, сохранение результатов и коллекции в захваченном окружении могут
иметь другой профиль памяти. Счётчик не учитывает накладные расходы системного
аллокатора, стек, отображения памяти или выделения C-библиотек в обход GlobalAlloc.

## Память процесса по macOS `/usr/bin/time -l`

Это maximum resident set size всего процесса, в МиБ (байты / 1048576), включая
исходник, компиляцию, runtime и системный аллокатор. Отдельные процессы для каждой
строки и режима. Повторный режим включает 18 исполнений, одиночный — одно проверенное.

| N | Eager: один запуск | Lazy: один запуск | Eager: 18 запусков | Lazy: 18 запусков |
| ---: | ---: | ---: | ---: | ---: |
| 1 000 | 2.19 | 1.97 | 2.55 | 2.25 |
| 100 000 | 12.34 | 1.97 | 144.56 | 2.22 |
| 1 000 000 | 92.47 | 1.97 | 1608.30 | 2.22 |

У eager RSS заметно растёт между запусками, хотя счётчик живых Rust-выделений
возвращается к baseline. Причина роста RSS этим экспериментом не установлена;
нужен отдельный профиль аллокатора/ОС. Нельзя трактовать RSS как размер живых
значений Rush или как доказанную утечку runtime.

## Воспроизведение

```sh
RUSH_BENCH_CASE=collections RUSH_BENCH_ITEMS=1000000 RUSH_BENCH_ITERS=1 \
RUSH_BENCH_OPERATION=prepared_run \
cargo bench --locked -p themoretheless-tokenizer-rush --bench runtime

# Повторить с RUSH_BENCH_CASE=collections_lazy.
cargo bench --locked -p themoretheless-tokenizer-rush --bench memory
```

Для замера RSS сначала собрать `cargo bench --no-run ... --bench runtime` и
запустить напечатанный путь Executable напрямую через `/usr/bin/time -l` с теми же
переменными окружения. Cargo не должен входить в измеряемый процесс.
`RUSH_BENCH_OPERATION=verify` выполняет ровно один проверяемый запуск без прогрева.
Число микросекунд в этом режиме — одиночное наблюдение, не медиана серии; оно
исключает удаление результата и служит вспомогательной диагностикой.

## Следующие измерения

- Найти источники примерно 8.7 выделений на элемент; уменьшение их числа может
  помочь обоим способам обхода. Первый профиль вызовов приведён ниже; основной кандидат — копирование окружений.
- Исследовать удержание RSS при повторных eager-запусках отдельно от живой кучи.
- Расширить замер отмены на другие размеры eager-значений и реальный host API;
  сравнить одинаковые программы с другими языками.
- Решение о bytecode пока не обосновано: этот замер его не сравнивает с AST.

## Удаление временных списков аргументов

Следующий замер использует тот же вычислитель с одним изменением: обработчики
коллекций получают заимствованный срез аргументов вместо отдельного `Vec` на
каждый вызов. Обычные вызовы из AST продолжают владеть вычисленными аргументами;
встроенные функции материализуют принадлежащий им список, если он нужен для
возвращаемого значения. Бюджет исполнения и проверки типов сохранены.

| Миллион элементов | Выделения до | Выделения после | Изменение |
| --- | ---: | ---: | ---: |
| Eager | 8 666 769 | 6 333 435 | −2 333 334 (26.92%) |
| Lazy | 8 666 713 | 6 333 379 | −2 333 334 (26.92%) |

Это соответствует одному устранённому выделению на вызов: миллион `map`,
миллион `filter`, 333334 вызова `fold`. Пики дополнительных живых байтов после
изменения — 83901432 для eager и 24064 для lazy. Во всех трёх повторах каждого
размера живые выделения после удаления результата вернулись к baseline.

При отдельном последовательном замере после завершения тестов медианы на миллионе
элементов составили 965.714 мс (eager) и 864.499 мс (lazy).
Применены прежние 10 прогревов и 7 измерений по одному запуску. Это локальные
наблюдения после изменения, а не чередующийся A/B-тест; устойчивый процент ускорения
по ним не заявляется. Снижение числа выделений непосредственно измерено счётчиком.
RSS после этой оптимизации не перемерялся.

Проверены возврат вложенных значений из builtin callbacks, захват аргументов
возвращаемыми замыканиями, lazy/eager цепочки, отмена и ошибки. Тесты workspace
со всеми targets/features и Clippy Rush прошли.

[Полные результаты после изменения](benchmarks/rush-borrowed-arguments-2026-10-01.txt).

SHA-256 обновлённого `runtime.rs`: `05cd326ee63acbd5f9d9e6867d69717f8af3f3dd53435505f26c2e537a71c726`.


## Задержка отмены из другого потока

Команда: `cargo bench --locked -p themoretheless-tokenizer-rush --bench cancellation`.
Платформа и runtime те же, что в предыдущем разделе. Каждый сценарий получает
новый CancellationToken. Callback `ready` сообщает второму потоку, что исполнение
началось. Этот поток ждёт 5 мс, записывает Instant и вызывает `cancel()`.
Основной поток измеряет время до возврата `run_with_host`, включая очистку runtime.
Компиляция и запуск потока до сигнала в задержку не входят. Планирование обоих
потоков ОС входит в наблюдаемые значения.

Два прогрева и 25 измерений на сценарий. Все исполнения обязаны завершиться именно
ошибкой `Execution cancelled`; исчерпание бюджета или обычный возврат не засчитываются.
P95 — 24-е значение отсортированной серии из 25 (nearest-rank). Верхний предел
задержки не проверяется assert: этот benchmark не превращает нагрузку ОС в падение CI.

| Сценарий | Медиана, мкс | P95, мкс | Максимум, мкс |
| --- | ---: | ---: | ---: |
| `while true {}` | 1.875 | 2.667 | 2.750 |
| Построение `range(0, 1000000000000)` | 2526.375 | 5270.667 | 5433.791 |
| Lazy-фильтр, отклоняющий все элементы, затем `collect(1)` | 4.584 | 6.584 | 6.917 |
| Callback хоста с `sleep(20ms)`, игнорирующий токен | 17653.666 | 18744.542 | 19573.625 |

Eager-диапазон возвращает управление существенно позже lazy-фильтра. В измерение
входит освобождение уже созданного списка; вклад очистки и планировщика здесь
не разделён. Число элементов eager-списка к моменту отмены зависит от скорости
процессора, поэтому это не сравнение одинакового накопленного объёма данных.

Блокирующий callback сам выставляет сигнал начала и затем спит. Отмена не
прерывает callback: runtime обнаруживает токен после его возврата. Отрицательная
проверка подтверждает границу кооперативной отмены, а не обещает предел 20 мс для
любого хоста. Эти результаты относятся к нативному Rust runtime; отмена браузерного
Web Worker измеряется другим механизмом и здесь не проверена.

[Полный вывод](benchmarks/rush-cancellation-2026-10-01.txt).

SHA-256 `benches/cancellation.rs`: `da8f3b058ab82e3404442ee974d7265c6f9d4ebbf80e4534859d1b46a162122c`.

## Профиль вызовов lazy-сценария

2026-10-01: macOS `sample`, 5 секунд с интервалом 1 мс, отдельный процесс
benchmark `runtime` с `CARGO_PROFILE_BENCH_DEBUG=1`. Сценарий — прежний
`collections_lazy`, миллион элементов, подготовленная программа. Получено
4 146 снимков основного потока. Результат вычисления проверен benchmark;
процесс завершился с кодом 0. [Исходный профиль и параметры](benchmarks/rush-call-profile-2026-10-01.txt).

В таблице указаны верхние кадры стека, без суммирования вложенных вызовов:

| Верхний кадр | Снимки | Доля всех снимков |
| --- | ---: | ---: |
| Копирование hashbrown RawTable с Binding | 1 170 | 28.2% |
| mach_absolute_time | 597 | 14.4% |
| Удаление Value | 526 | 12.7% |
| Удаление RawTable с Binding | 489 | 11.8% |
| Runtime::inner | 195 | 4.7% |

Это выборка одного числового сценария, а не точный подсчёт вызовов или прогноз
ускорения. Оптимизация и inlining влияют на привязку к кадрам. `mach_absolute_time`
в дереве встречается под системным освобождением памяти; профиль не позволяет
приписать все такие затраты проверке времени самим Rush.

В `Runtime::call` перед привязкой параметров выполняется
`function.environment.clone()`. Дерево профиля показывает копирование таблицы
под вызовами функций в `sequence_next`. Следующий обоснованный эксперимент —
сократить копирование захваченного окружения при вызове, сохранив лексические
снимки, общие изменяемые ячейки, рекурсию и владение вышедшими из вызова замыканиями.
Проверять эффект следует прежними benchmark времени и живых выделений.

Время серии под профилировщиком не используется для сравнения производительности:
профилирование меняет нагрузку. Этот профиль также не объясняет удержание RSS
в eager-сценарии и не обосновывает переход к bytecode.

## Общие окружения замыканий

По результатам профиля изменён `Runtime::call`: захваченное окружение хранится
в `Rc`, вызов создаёт отдельную локальную таблицу и ссылается на него как на
родительское. Поиск имени проходит по родительским окружениям без рекурсивного
вызова Rust. Создание замыкания по-прежнему делает снимок локальных имён;
изменяемые переменные сохраняют общие ячейки текущего исполнения.

Сравнение на том же миллионе элементов, `collections_lazy`, обе сборки
`optimized + debuginfo`, без профилировщика. Последовательность отдельных процессов:
до → после → после → до. В каждой серии 10 прогревов и 7 измерений.

| Серия | Медиана, мс |
| --- | ---: |
| До, первая | 838.298 |
| После, первая | 346.885 |
| После, вторая | 342.551 |
| До, вторая | 808.691 |

В этом сценарии время уменьшилось примерно в 2.4 раза. Это локальное сравнение
одного сценария; глубокие цепочки захватов и другие программы требуют отдельных
замеров. Снимки окружений при создании замыканий всё ещё копируют локальную таблицу.

Пик живых выделений lazy составил 20 748 байтов, eager — 83 898 052 байта.
Число выделений — 6 333 382 и 6 333 438 соответственно: практически прежнее,
с тремя дополнительными выделениями для трёх замыканий. Выигрыш достигнут
сокращением копирования содержимого окружения. Во всех 18 замерах памяти живые
байты после удаления результата вернулись к baseline.

[Полные измерения и хеши исходника](benchmarks/rush-shared-environments-2026-10-01.txt).
Регрессионный тест `shared_environments_keep_call_frames_and_snapshots_independent`
проверяет отдельные вызовы фабрики, общие `mut`, замыкания из `map`, затенение,
саморекурсию и повторное исполнение подготовленной программы.

## Повторная проверка RSS и системного аллокатора

После оптимизации окружений и исправления арифметики диапазонов рост максимального
RSS eager воспроизводится. На миллионе элементов `/usr/bin/time -l` дал
96 911 360 байтов за одно исполнение и 1 686 454 272 за 18. Для lazy —
2 064 384 и 2 326 528 байтов. Каждый режим выполнялся в отдельном процессе;
результат проверен. Унаследованная настройка среды: `MallocNanoZone=0`.

Добавлен отдельный macOS benchmark `allocator`. Он выполняет 18 проверенных
запусков, удаляет результат и читает `malloc_zone_statistics(NULL, ...)` по всем
зонам. Режим `RUSH_BENCH_RELIEF=1` дополнительно вызывает
`malloc_zone_pressure_relief(NULL, 0)` после каждого исполнения. Семантика и ABI
взяты из установленного macOS SDK `malloc/malloc.h`; эти вызовы не добавлены
в runtime или обычные измерения времени.

В обеих сериях после каждого запуска оставалось 226 блоков и 19 424 байта
`size_in_use`, ровно как до запуска. Резерв `size_allocated` стабилизировался
на 29 360 128 байтах (28 МиБ). Relief каждый раз возвращал 0 освобождённых байтов.
Таким образом, эти счётчики не подтверждают гипотезу о накоплении живых объектов
или резервов malloc на величину наблюдаемого максимального RSS. Они также не
доказывают отсутствие другого удержания: нужна синхронная проверка текущих
resident/footprint и VM-регионов внутри того же процесса. Максимальный RSS и
статистика malloc измеряют разные величины и не взаимозаменяемы.

```sh
cargo bench --locked -p themoretheless-tokenizer-rush --bench allocator
RUSH_BENCH_RELIEF=1 cargo bench --locked -p themoretheless-tokenizer-rush --bench allocator
# RUSH_BENCH_LAZY=1 выбирает тот же сценарий с range_iter.
```

На других ОС benchmark сообщает, что нужны средства macOS. Переносимый benchmark
`memory` остаётся проверкой живых Rust-выделений.
[Сырые результаты и хеш runtime](benchmarks/rush-allocator-2026-10-01.txt).

## Текущая память и VM-регионы после исполнения

В `allocator` добавлены `proc_pid_rusage(RUSAGE_INFO_V0)` после каждого исполнения
и необязательное ожидание ввода `RUSH_BENCH_WAIT=1` для внешнего снимка `vmmap`.
ABI взят из установленного SDK `sys/resource.h` и `libproc.h`. Ошибка чтения
счётчиков завершает benchmark с диагностикой, а не превращается в нулевую память.

Текущие resident size и physical footprint растут вместе с числом eager-запусков:
примерно на 89 МиБ каждый раз. Следовательно, прежний результат не объясняется
только особенностями максимального счётчика `/usr/bin/time`.

После 18 проверенных исполнений и удаления всех результатов `vmmap -summary`
показал **54 региона `MALLOC_LARGE (empty)`**, вместе **1.8G virtual, 1.6G resident
и 1.6G dirty** (округлённые единицы самого vmmap). Таблица живых malloc-зон при
этом показала 220 выделений и около 27K allocated. Это локализует основную
резидентную память в регионах, помеченных как пустые, и согласуется с переносимым
счётчиком Rust, возвращающимся к baseline после удаления результатов.

Наблюдение относится к этой версии macOS и аллокатора, с `MallocNanoZone=0`.
Оно не объясняет точную политику удержания пустых крупных регионов или нулевой
ответ pressure relief. Изменений системных настроек и вызовов pressure relief
в runtime не сделано. Лимит живых данных и ограничение физической памяти процесса
должны учитываться отдельно: первое само по себе не гарантирует второе.

Для воспроизведения собрать `allocator` через `cargo bench --no-run`, запустить
полученный executable с `RUSH_BENCH_WAIT=1`, дождаться `READY_FOR_VMMAP PID`,
снять `/usr/bin/vmmap -summary PID`, затем отправить перевод строки в stdin.
[Синхронные счётчики и карта памяти](benchmarks/rush-allocator-vm-2026-10-01.txt).

## Контроль политики кэша крупных блоков

В открытом [исходнике Apple libmalloc](https://github.com/apple-oss-distributions/libmalloc/blob/main/src/malloc.c)
переменная `MallocLargeCache` принимает 0/1 и управляет `large_cache_enabled`.
Это источник гипотезы; просмотренная ветка main не является доказательством точного
исходника установленной macOS. Проверка поведения проведена на локальном бинарнике:
переменная задавалась только перед запуском отдельного benchmark-процесса.

При одинаковых 18 eager-исполнениях по миллиону элементов:

| Настройка процесса | Текущий RSS после 18 запусков, байты | Physical footprint, байты |
| --- | ---: | ---: |
| `MallocLargeCache=1` | 1 686 421 504 | 1 686 505 128 |
| `MallocLargeCache=0`, первый опыт | 3 817 472 | 1 589 536 |

## Отмена в браузерном Web Worker

2026-10-01, встроенный Chromium 154 на macOS, release WASM текущей рабочей копии.
[Сырые измерения](benchmarks/rush-browser-cancellation-2026-10-01.json).
Стенд использует production `rush-worker.js` и `executeInWorker`; обёртка WASM
сообщает о входе в `run_rush`, после чего основной поток ставит таймер отмены
на 1 мс. Загрузка WASM происходит до этой отметки. Время от отметки считается
с момента получения сообщения основным потоком, поэтому не включает его доставку.

Сценарий: `while true { let xs = range(0,1000) | map(x => x*x) }`.
Три контрольных запуска достигли лимита шагов за 10.5–10.7 мс после получения
отметки. Все 20 последующих запусков завершили Promise ошибкой
`Execution cancelled`: от получения отметки до результата прошло 1.1–2.0 мс,
от вызова `abort()` до результата — 0–0.1 мс. Ноль здесь означает отсутствие
различия при доступной точности часов, а не нулевую физическую задержку.
После серии новый worker успешно вычислил `1+2` как `Number(3.0)`.

Это измерение реакции Promise и синхронного вызова `Worker.terminate()`.
API не подтверждает момент завершения системного потока или освобождения его
памяти; эти величины не измерены. Нагрузка основной страницы, фоновые вкладки,
другие браузеры и холодный запуск могут изменить результат. Замер не является
гарантией максимальной задержки. Инструментальная обёртка добавляет одно сообщение
перед вычислением; в обычном playground этого сообщения нет.

Воспроизведение:

```sh

npm --prefix playground run dev -- --host 127.0.0.1 --port 4182 --strictPort
```

Открыть `/benchmarks/cancellation.html` и нажать **Run benchmark**. Стенд отклоняет

### После добавления сборки циклических ячеек

Runtime теперь периодически строит граф ссылок между ячейками, замыканиями,
окружениями и последовательностями. Для каждого Rc-объекта число известных
входящих ссылок сравнивается с strong_count; оставшиеся ссылки считаются
внешними корнями. Сборщик сохраняет всё достижимое от корней и очищает значения
недостижимых ячеек. Граф обходится через явную очередь без рекурсии, учитывает
бюджет шагов и отмену. Период зависит от числа оставшихся живых ячеек, с минимумом
64 новых ячеек между обходами. Сборка сама использует временную память.

Повтор той же серии, теперь с циклическим вариантом и при N=10 000:

| Локальная mut в функции | 39 348 | 39 348 | 39 348 |

Все числа — дополнительные живые байты, включая временный граф сборщика.

### После ограничения захвата используемыми именами

Program сохраняет уже полученные при анализе лексические ссылки. При создании
замыкания runtime выбирает внешние имена из его диапазона исходника и копирует
только соответствующие bindings. Параметры и локальные объявления определяются
по позиции определения; обращения внутри вложенной функции также учитываются.
Метаданные исходника разделяются через Rc между программой и её замыканиями.

байт вместо 255 039 при N=100, 1000 и 10 000. Код сценария не менялся: финальная
lambda `() => f` не использует local и поэтому больше не удерживает его список.

[Полный вывод](benchmarks/rush-cell-memory-captures-2026-10-01.txt).
Это пик исполнения сверх baseline после компиляции: дополнительная память
метаданных подготовленной программы в эти числа не входит. Время создания
замыканий после этого изменения отдельно пока не измерено.

## Первый эксперимент: дерево выражений и стековые инструкции

Добавлены `benches/support/scalar.rs`, `benches/scalar_bytecode.rs` и
`tests/scalar_bytecode_experiment.rs`. Это отдельный эксперимент; публичный
Program и рабочий исполнитель Rush не изменены.

Rush-парсер разбирает скалярное выражение. Общая подготовка преобразует числа
в f64 и имена параметров в индексы. Первый исполнитель рекурсивно обходит
полученное дерево; второй выполняет линейный массив инструкций Enter, Constant,
Local и Binary. Enter сохраняет проверку отмены и расход бюджета в том же
порядке, что обход дерева. Код инструкций создаётся только доверенным compiler;
загрузки произвольного байткода нет. Стек VM выделен заранее и повторно используется.

Поддержаны числа, bool, параметры и операторы +, -, *, /, %, ==, <.
Другие конструкции явно отвергаются при подготовке. Нет ветвлений, вызовов,
замыканий, объектов хоста или коллекций внутри этих исполнителей. Размер
выражения ограничен глубиной 64. Это массив Rust enum-инструкций, без упаковки
в компактный бинарный формат, register allocation или JIT.

В этой серии инструкции быстрее подготовленного дерева примерно на 15–18%.

## Ветвления в скалярном эксперименте

Прототип расширен выражениями `if` и операторами `and/or`, `&&/||`.
Для разбора отдельного верхнеуровневого if-выражения используется запись
`(if condition { value } else { value })`; операторы if в блоке не добавлены.
VM использует Jump, JumpIfFalse, ShortCircuit и EnsureBool. Условие if снимается
со стека; при коротком вычислении логический результат остаётся на стеке.
Переходы пропускают и вычисления, и инструкции Enter невыбранной ветки.
Максимальный стек определяется по дереву с учётом альтернативных веток.

Пятый тест сопоставляет 17 сценариев с рабочим Rush: обе ветки, вложенные
ветвления, неверный тип условия/операнда, ошибки выбранной ветки и пропуск
деления на ноль. Для каждого проверяются бюджеты 0..29, совпадение ошибок
между прототипами и неизменная ёмкость заранее выделенного стека. Дополнительно
зафиксированы минимальные бюджеты для короткого and/or (2 узла) и простого
if (3 узла). Прежние четыре теста также проходят.

Сценарий `branches`: map выбирает x*2 для чётных x и x для нечётных,
filter проверяет x%3==0 and x<15000, fold суммирует. Результаты проверены
независимым целочисленным алгоритмом и полным Rush для всех трёх размеров.
Методика прежняя: 10 прогревов и 8 чередующихся выборок по 100 цепочек.

| Элементов | Дерево с ветвлениями, медиана мкс | Инструкции с переходами, медиана мкс |
| ---: | ---: | ---: |
| 100 | 8.037 | 6.032 |
| 1000 | 90.256 | 69.363 |
| 10 000 | 968.490 | 762.908 |

[Исходные выборки ветвлений](benchmarks/rush-scalar-branches-2026-10-01.txt).
В этой серии разница составляет 21–25% в пользу инструкций. Повторён и исходный

[отдельные результаты](benchmarks/rush-scalar-jump-dispatch-2026-10-01.txt).

## Подготовка и память скалярных прототипов

Подготовка измерена отдельно без счётчика allocator: 10 прогревов каждой
операции, 9 выборок по 1000 подготовок, порядок трёх операций циклически
меняется. Замер включает освобождение результата. Parse+tree — Rush parse и
понижение в подготовленное дерево; tree→instructions — только генерация
инструкций из существующего дерева; parse+instructions — весь путь с
освобождением промежуточного дерева. Это подготовка выражений, а не полного
Program с анализом имён, модулями и замыканиями.

| Выражение | Parse+tree, мкс | Tree→instructions, мкс | Parse+instructions, мкс |
| --- | ---: | ---: | ---: |
| x*2 | 0.326 | 0.056 | 0.412 |
| if чётное x, то x*2, иначе x | 1.432 | 0.152 | 1.636 |
| x%3==0 and x<15000 | 0.954 | 0.156 | 1.131 |

[Все выборки подготовки](benchmarks/rush-scalar-preparation-2026-10-01.txt).
Медианы независимых операций не обязаны складываться: различаются время жизни
временных объектов и состояние allocator. Выигрыш повторного выполнения имеет
цену подготовки; результат однократного запуска этим замером не установлен.

Память снята отдельным бинарным бенчмарком `scalar_memory` со счётчиком
запрошенных живых байтов System allocator. Учтены успешные alloc/alloc_zeroed и
realloc, служебный код счётчика не выделяет память. Калибровка проверяет
выделение и освобождение 4096 байт. Для каждой операции — три повтора.

| Выражение | Хранимое дерево, Б | Хранимые инструкции, Б | Стек VM, Б | Пик полной подготовки, Б |
| --- | ---: | ---: | ---: | ---: |
| x*2 | 96 | 256 | 32 | 1096 |
| if чётное x, то x*2, иначе x | 432 | 1024 | 32 | 3336 |
| x%3==0 and x<15000 | 384 | 1024 | 32 | 2248 |

Пик полной подготовки совпал для двух путей в этой серии: выше всего временные
данные разбора. Размер хранимых инструкций включает свободную ёмкость Vec;
компактного кодирования и shrink_to_fit нет. Значения в таблице исключают
Rust-стек, inline-часть возвращаемых структур, расходы allocator и RSS.

Для каждого выражения отдельно проверены 1000 повторных выполнений дерева и
VM с готовым стеком. Все 18 таких серий зарегистрировали ноль allocation calls
и нулевой прирост heap. Результаты проверяются на каждом вызове. После drop
результатов всех 54 измерений живой heap вернулся к исходному уровню.
[Полный отчёт памяти](benchmarks/rush-scalar-memory-2026-10-01.txt).

Это закрывает подготовку и память только для текущего скалярного прототипа.
Замыкания, реальные host-вызовы и полная программа остаются необходимыми для
решения о backend Rush; общий лимит живой памяти рабочего runtime не добавлен.

```sh
RUSH_SCALAR_OPERATION=prepare cargo bench --locked -p themoretheless-tokenizer-rush --bench scalar_bytecode
cargo bench --locked -p themoretheless-tokenizer-rush --bench scalar_memory
```


## Скалярные вызовы хоста в двух прототипах

Оба исполнителя используют настоящие `HostFunction`, `HostCallback` и
`ValueType::accepts` рабочего Rush. При подготовке имя host-функции связывается
с Rc регистрации; bytecode хранит индекс регистрации. Аргументы вычисляются
слева направо, преобразуются в Value, проверяются по сигнатуре и передаются
callback. После успешного возврата проверяются отмена и тип результата.
Ошибка callback сохраняет текст и span вызова. Поддержаны только Number/Bool
в сигнатурах: opaque-объекты, списки, строки и другие значения не заявлены.

Шестой тест сравнивает 14 сценариев с рабочим Program: вложенные и соседние
вызовы, наблюдаемый порядок побочных эффектов, неверные типы/арность, бесконечный
числовой результат, ошибку callback, отмену внутри callback, пропущенную ветку
и ошибку аргумента. Для каждого также сверяются бюджеты 0..24 и журнал вызовов
между прототипами. Отмену блокирующего native-вызова этот тест не измеряет.
Сигнатуры вне скалярного подмножества и повторные имена отвергаются; параметр,
затеняющий имя host-функции, не трактуется как эта host-функция.

### Контроль выделения аргументов

Первый замер выявил различие адаптеров: сбор Result<Vec<Value>> в дереве
резервировал 160 Б для одного аргумента, сбор из готового среза VM — 40 Б.
[Исходный счётчик](benchmarks/rush-scalar-host-memory-2026-10-01.txt) и
[первый замер времени](benchmarks/rush-scalar-host-2026-10-01.txt) сохранены.
Дерево теперь явно резервирует число аргументов. Новый счётчик подтвердил
одинаковый пик 40 Б и 1000 allocation calls на 1000 одиночных host-вызовов
в обоих вариантах; после выполнения и drop прирост живого heap равен нулю.
[Повторный замер памяти](benchmarks/rush-scalar-host-equal-args-memory-2026-10-01.txt).
Вложенные вызовы могут иметь другой профиль времени жизни буферов; это не
доказательство одинаковых выделений для любых host-выражений.

### Выполнение с одинаковой ёмкостью буфера аргументов

map вызывает native double(x), filter — native selected(x), fold вычисляет
sum+x. Это прежнее преобразование чисел, но две операции вынесены в хост.

[Все выборки](benchmarks/rush-scalar-host-equal-args-2026-10-01.txt).

## Возвращаемые замыкания с неизменяемыми захватами

Добавлен `benches/support/closures.rs`: фабрика вида factor => x => x*factor
возвращает замыкание с сохранёнными значениями. Оба backend используют одинаковые
Rc-контейнеры захватов и сборку кадра параметров. Код тела разделяется между
экземплярами. Из захвата исключены неиспользуемые внешние параметры и имена,
затенённые внутренними параметрами.

Граница прототипа: создание и вызов замыкания выполняет Rust-стенд через bind/run.
В bytecode ещё нет общей инструкции вызова функции или создания произвольной
вложенной лямбды. Поддержаны ровно два уровня лямбд с именованными параметрами,
скалярными захватами и результатом. Изменяемые ячейки, рекурсия, замыкания как
аргументы других функций, три уровня и host-регистрации внутри фабрики не
реализованы. Это проверка представления захвата и выполнения тела, а не
эквивалент всего функционального runtime Rush.

Два новых теста довели набор до восьми. Пять фабрик на 20 аргументах каждая
сопоставлены с рабочим Rush. Проверены удаление исходной строки и фабрик до
вызова, независимые экземпляры, несколько захватов, bool-захват, затенение,
исключение неиспользуемых имён, бюджеты 0..19, неверная арность, ошибка тела,
повторный вызов и отмена до запуска. Старые тесты scalar/branch/host проходят.

### Время

Измеряется сумма triple(x) по N элементам. Каждый результат проверяется
независимой целочисленной суммой; аналогичная полная программа Rush проверена

операндов VM выделен заранее. В create_and_call замыкание создаётся и удаляется
для каждого элемента, но подготовка фабрики исключена.

| 100 | 4.302 / 4.442 | 9.313 / 9.468 |

### Heap

Для одного захвата у обоих вариантов bind делает два выделения с пиком 48 Б
и сохраняет 32 Б. Тысяча вызовов готового замыкания делает 1000 выделений кадров
с пиком 32 Б. Создание и вызов 1000 экземпляров — 3000 выделений с пиком 64 Б.
Счётчик исключает существующий код фабрики и заранее выделенный стек VM;
измеряет запрошенные байты, не RSS. По три повтора каждого сценария: после

остаются незавершёнными задачами.

## Рабочий AST: числовые литералы без временной строки

В ExprKind::Number раньше каждый вызов replace('_', "") создавал String,
включая обычные литералы 0, 2 и 3. Теперь при отсутствии подчёркивания parse
читает исходный &str через Cow::Borrowed. Прежнее удаление разделителей остаётся
для строки с подчёркиванием. Правила f64, проверки конечности, span ошибки,
порядок вычисления и бюджет не менялись. Это изменение рабочего runtime;
экспериментальный bytecode не используется.

Проверены все Rush targets; отдельная регрессия проверяет знак отрицательного
нуля по битам, минимальное субнормальное число, f64::MAX, дробную экспоненту,
underflow к нулю, отказ для 1e309 с прежним span и отсутствие ошибки в
невычисляемой ветке. Clippy всех targets также прошёл.

### Выделения

Существующий memory bench получил RUSH_MEMORY_ITEMS для выбора одного из
поддержанных размеров. Для N=1000 выполнено по три повтора до и после изменения.
Программа и проверка суммы одинаковы; исходные результаты:
[до](benchmarks/rush-literal-before-memory-2026-10-01.txt),
[после](benchmarks/rush-literal-after-memory-2026-10-01.txt).

| Сценарий | Allocation calls до / после | Пик запрошенного heap до / после, Б |
| --- | ---: | ---: |
| eager | 6407 / 3404 | 90400 / 90392 |
| lazy | 6381 / 3378 | 9960 / 9960 |

Удалены 3003 выделения в каждом выполнении. Во всех повторах после drop
прирост живого heap — ноль. Уменьшение числа выделений практически не изменило
пик памяти: временные строки были короткими и быстро освобождались.

### Время

Перед изменением сохранён optimized runtime bench, после изменения — второй
бинарный файл. Их SHA-256 и общие параметры записаны в JSON. Шесть пар процессов
