# Rush: дизайн лимитов памяти (draft)

Дата: 2026-10-24. Ветка `language-improvements`, локальный macOS/aarch64. Это
дизайн-документ: реализация не написана, семантика runtime не менялась. Все числа
воспроизводимы командами из [инвентаризации](benchmarks/rush-memory-inventory-2026-10-24.txt)
(далее — «инвентаризация»).

## 1. Контекст и измеренная мотивация

Сегодня Rush ограничивает выполнение шагами (`ExecutionLimits.steps`,
runtime/types.rs:843), глубиной, пооперационными размерами
(`max_collection_items` / `max_string_bytes`, runtime.rs:804-821) и живыми
данными инстанса (`set_memory_limit`, runtime/instance.rs:442-466). Инвентаризация
показала три класса памяти, которые не видит ни один из этих механизмов:

| Класс | Измерение | Источник |
| --- | --- | --- |
| AST + токены после parse | 33–58 байт на байт исходника; источник 16 МиБ (дефолт `max_input_bytes`) → ~0,5–0,9 ГиБ parse-side heap | инвентаризация §4, `cargo bench --locked -p themoretheless-tokenizer-rush --bench inventory` |
| Транзиентный пик eager-вычисления | 98 347 616 байт пик при 0 живых байтах после run (1M элементов); lazy тот же обход держит в ~21 КБ | инвентаризация §3, `--bench memory` |
| «Работа без остатка» | конкатенация `s = s + 'x'` ×10 000: 250 108 640 байт суммарно выделено при живом результате 10 000 байт (~25 000×); пик при этом ~60 КБ | инвентаризация §5 |

Почему существующие лимиты каждый класс не ловят:

- Шаги тарифицируют операции, а не байты: `range(0, 1_000_000)` — один шаг.
- Живой heap (retained budget) смотрит только на остаток на границах вызовов;
  пик 98 МБ и кумулятивные 250 МБ оставляют остаток 0 / 10 КБ.
- `max_collection_items` / `max_string_bytes` — пооперационные проверки
  `current + added` (runtime.rs:804-821): они ограничивают размер одного
  значения, не сумму и не пик.
- `max_tokens` считает *количество* токенов (lexer.rs:29), а не байты AST.

## 2. Предлагаемая модель: три независимых лимита

Лимиты независимы: любой подмножеством можно управлять отдельно, исчерпание
одного не влияет на учёт остальных.

### 2a. Parse-time байтовый лимит (`max_ast_bytes`)

> **Статус: реализовано 2026-10-24 (этот коммит).** Поле `max_ast_bytes`
> добавлено в `InputLimits` (crates/tokenizer-core/src/limits.rs), дефолт и
> деривация от `max_input_bytes` — как ниже; учёт — в
> crates/tokenizer-rush/src/parser.rs (оценка запрошенных байт по узлам,
> см. `stmt_bytes`/`expr_bytes`); ошибка — диагностика `ast-limit`
> «Parse output byte limit exceeded»; тесты — crates/tokenizer-rush/tests/limits.rs.

**Что считается.** Байты, удерживаемые результатом `parse_with`: вектор токенов
`Lexed` и дерево `Module` (ast.rs:39-207). Измеренная плотность — 33–58 Б/байт
источника (инвентаризация §4), поэтому оценку можно делать либо точно (считающий
аллокатор / явный подсчёт по узлам на этапе построения), либо дешёвой верхней
оценкой `tokens * size_of::<LexToken>() + source.len() * K` с задокументированным K.

**Когда проверяется.** Во время `parse_with` / `Program::compile`: при превышении —
диагностика parse-уровня, а не ошибка выполнения. Действует до запуска и не
зависит от данных выполнения.

**Ошибка.** В стиле существующих входных лимитов — диагностика в
`Parse::diagnostics` (с учётом `max_diagnostics`), программа не компилируется.

**Умолчание.** Предлагается консервативный дефолт, а не off: вывести из
`max_input_bytes` — `max_ast_bytes = 64 * max_input_bytes` покрывает измеренный
максимум 58 Б/байт с запасом и не ломает ни один легальный источник, проходящий
сегодня. `InputLimits::conservative()` тогда даёт ~1 ГиБ — щедро, но конечно.
Хост, выставляющий жёсткий `max_input_bytes`, автоматически получает
соразмерный потолок AST.

**Оверхед.** Нулевой для выполнения; на parse — одно накопление на узел/токен
(уже делается для `max_tokens` по количеству).

### 2b. Пиковый heap-бюджет на run (`max_heap_bytes`)

> **Статус: реализовано 2026-10-24 (этот коммит).** Поле `max_heap_bytes`
> добавлено в `ExecutionLimits` (runtime/types.rs, дефолт `usize::MAX` — off);
> `Budget` создаётся с конечным лимитом (runtime.rs). Дополнительно к
> драфту: eager-материализации `range`/`map`/`filter`/`flat_map`/`group_by`/
> `collect` строятся в обычных `Vec` вне журнала, поэтому добавлен
> `memory::Cover` (runtime/memory.rs) — резервация, догоняющая capacity
> вектора и освобождающаяся при выходе из операции; без него пик 98 МБ лимит
> не увидел бы. Ошибка — «Heap limit exceeded» через
> `AllocationError::message`; калибровка — `ScriptInstance::peak_heap_bytes()`.
> Тесты — crates/tokenizer-rush/tests/limits.rs (граница «peak / peak−1»,
> терминальность корутины, lazy-отказ без протухших резерваций, независимость
> от retained-data budget). Bytecode VM лимит не применяет (vm.rs:53-63
> читает только steps/max_depth) — задокументировано в спеке и README.

**Что считается.** Задействовать существующий `Budget`/`Reservation`
(runtime/memory.rs:53-133), который уже считает байты для `Slots` (ячейки,
module_cache, буферы последовательностей) и `Shared` (окружения, захваты), но
создаётся с `usize::MAX` (runtime.rs:584). Лимит заменяет `usize::MAX` на
конечное значение; `Ledger` уже ведёт `live` и `peak` (memory.rs:54-58).

**Покрытие и честная граница.** Это закрывает только те пути, которые уже
проходят через `Budget`. Инвентаризация §3 измеряла пик *всеми* аллокациями
процесса (считающий `GlobalAlloc`), а `Budget` покрывает подмножество — ячейки,
окружения, буферы последовательностей. Строки-результаты конкатенации и
временные `Vec` арифметики через `Budget` сегодня не идут. Чтобы 98-МБ
eager-пик реально упёрся в лимит, буферы материализации `range(...)`
(уже `memory::Buffer`, sequence.rs:177-226) должны оставаться на этом бюджете —
это так, но любые новые eager-пути вне `Budget` лимит не увидят. Это следует
зафиксировать тестом, а не предполагать.

**Когда проверяется.** На каждом `reserve` внутри `Budget` (уже возвращает
`LimitExceeded`, memory.rs:103-110) — семантика «grow перед аллокацией, shrink
после освобождения» сохраняется (memory.rs:113-127). Дополнительно значение
`peak` доступно хосту после run для калибровки (сейчас `peak_bytes` только
`#[cfg(test)]`, memory.rs:87-90).

**Ошибка.** `AllocationError::Limit` сегодня маппится в ошибки runtime; на
уровне скрипта текст в стиле существующих — например, «Heap limit exceeded»
рядом с «Execution limit exceeded» (runtime.rs:839), «Collection item limit
exceeded» (runtime.rs:818), «String byte limit exceeded» (runtime.rs:809).

**Умолчание.** Off (`usize::MAX`) для обратной совместимости: в отличие от 2a,
здесь нет измеренной пропорции к размеру входа, из которой можно вывести
безопасный дефолт; любой конечный дефолт отвергнет какую-то программу,
которая сегодня работает. Хосты с реальным потолком выставляют его явно;
`peak` после run даёт им измеренную отправную точку.

**Оверхед.** Минимальный: резервации и арифметика `live`/`peak` уже выполняются
на каждой аллокации через `Budget`; добавляется одно сравнение `next > limit`
(уже есть в `Reservation::resize`, memory.rs:116-126) — фактически меняется
только начальное значение поля `limit`.

### 2c. Кумулятивный бюджет аллокаций за run (`max_allocated_bytes`)

> **Статус: реализовано 2026-10-24 (этот коммит).** Поле `max_allocated_bytes`
> в `ExecutionLimits` (дефолт off), счётчик `allocated` в `Ledger`
> (runtime/memory.rs), зарядка в `string_growth` (размер нового буфера
> результата), `collection_growth` (маргинальные элементы × `size_of::<Value>()`)
> и `memory::Cover` (рост capacity eager-буферов). Ошибка «Allocation limit
> exceeded». Уточнения к драфту по коду: (1) `collection_growth` заряжает
> маргинальные `added`, а не `current + added`, иначе амортизированный рост
> Vec давал бы ложное квадратичное списание и ломал легальные циклы;
> (2) резервации Slots/Shared кумулятивно не заряжаются — они под пиковым
> лимитом, а смешение давало бы неверное сообщение об ошибке; (3) оба бюджета
> следуют per-call `ExecutionLimits` (`ScriptInstance::call`,
> `coroutine_limits`), как steps; (4) калибровка —
> `ScriptInstance::allocated_bytes()`. Тесты — tests/limits.rs (граница
> «allocated / allocated−1», контроль «2b молчит, 2c ловит», независимость от
> retained и отмены). Bytecode VM по-прежнему не покрыт.

**Что считается.** Сумма `added` по существующим точкам `string_growth` /
`collection_growth` (~50 вызовов в expr.rs, calls.rs, stmt.rs, sequence.rs) —
то есть байты, *запрошенные* операциями за весь run, включая давно освобождённые.

**Мотивация.** Это единственная метрика, которая видит «работу без остатка»:
квадратичная конкатенация выделяет 250 МБ суммарно при пике ~60 КБ и живом
результате 10 КБ (инвентаризация §5). Ни пиковый (2b), ни живой бюджет это не
ловят принципиально. `steps` сегодня частично покрывает класс (каждая итерация
— шаги), но тарификация не в байтах: 10 000 шагов могут скрывать 250 МБ.

**Когда проверяется.** В тех же вызовах `string_growth` / `collection_growth`:
`allocated += added; if allocated > max_allocated_bytes { error }`. Проверка
происходит до выполнения операции (как сейчас проверка размера результата),
поэтому квадратичный цикл останавливается раньше исчерпания системной памяти.

**Ошибка.** «Allocation limit exceeded» в том же стиле (runtime.rs:829-845).

**Умолчание.** Off, по той же причине, что 2b: кумулятивный объём зависит от
алгоритма скрипта, а не от размера входа. Отдельное соображение: включённый
по умолчанию кумулятивный лимит меняет смысл существующих сценариев с длинными
lazy-пайплайнами, которые сегодня легально выделяют много суммарно при малом
пике.

**Оверхед.** Одно сложение и одно сравнение на вызов в точках, которые уже
делают арифметику лимитов; на горячих путях без строк/коллекций — ноль.

## 3. Явно вне объёма

- **Аллокации host-колбэков.** Принципиально непрозрачны: код хоста выполняется
  вне счётчиков, «host-owned allocations are opaque» (runtime/instance.rs:259).
  Контракт остаётся прежним: результат проверяется после возврата
  (`host_value_size`, runtime.rs:760-803), лимиты 2b/2c на внутренности колбэка
  не распространяются. Это граница, которую нужно документировать, а не
  закрывать.
- **RSS процесса и удержание аллокатора.** Рост RSS на macOS объяснён политикой
  MallocLargeCache, а не утечкой (docs/rush-performance.md:280-340). Рекомендация
  хостам — переменная окружения `MallocLargeCache` / давление
  `malloc_zone_pressure_relief` — относится к README/документации хоста, не к
  runtime-лимитам.
- **Bytecode VM.** VM имеет только `fuel` (= `limits.steps`, bytecode/vm.rs:31,
  55, 198-215) и не пользуется `Budget`/`Reservation` — grep по
  `crates/tokenizer-rush/src/bytecode*.rs` не находит ни одного обращения к
  `memory::`. Стек/кадры VM — обычные `Vec::with_capacity` (vm.rs:47-49).
  Лимиты 2b/2c в предлагаемом виде VM **не покрывают**; если bytecode-режим
  должен получить те же гарантии, это отдельная работа (свои точки учёта в
  аллокаторах значений VM), и её следует явно назвать в плане, а не считать
  включённой.
- **Аллокаторный оверхед и выравнивание.** Все лимиты считают запрошенные
  байты, а не реальные footprint аллокатора (та же оговорка, что в
  memory.rs:1-2 и в bench `memory`: «Requested heap bytes; stack/allocator
  overhead/RSS excluded»).

## 5. Открытые вопросы

1. **Взаимодействие 2b с retained-data budget инстанса.** `set_memory_limit`
   считает живые байты логически (`Usage`, instance.rs:260-383), 2b — байты
   резерваций через `Budget`. Механизмы разные по покрытию (Usage видит
   `Value`, Budget — `Slots`/`Shared`) и по моменту проверки (границы вызовов
   против точек роста). Предложение: оставить оба, задокументировав 2b как
   лимит *выполнения*, а retained budget — как лимит *состояния инстанса*;
   не пытаться выводить один из другого.
2. **Корутины.** `enforce_memory_limit` вызывается из scheduler
   (coroutine.rs:398, 479); резервации корутинных кадров при исчерпании 2b
   должны приводить к ошибке задачи, а не к панике scheduler'а. Нужен тест
   «coroutine исчерпывает heap-бюджет посреди yield-цикла» до включения 2b
   по умолчанию у какого-либо хоста.
3. **Lazy-последовательности и 2b посреди итерации.** Буферы материализации
   резервируются при сползании (sequence.rs:177-226); отказ посреди итерации
   обязан оставлять последовательность в состоянии, где ошибка — единственный
   наблюдаемый эффект (тот же инвариант «reserve до аллокации, shrink после
   освобождения», memory.rs:113-127). Покрыть тестом на отказ посередине.
4. **Захваты замыканий.** Окружения уже идут через `memory::Shared`
   (env.rs:194-213) и потому покрываются 2b; отдельный лимит не нужен, если
   не появится требование различать «память данных» и «память замыканий» —
   сейчас такого требования нет, а измеренные доли (cells-кейсы инвентаризации
   §3: пики 10–75 КБ) малы по сравнению с eager-пиками.
5. **Точный или оценочный учёт в 2a.** Точный подсчёт байт по узлам AST
