# Сравнение Rush и скриптовых языков: измерения и контракты

Дата: 2026-10-01. macOS 26.7, arm64. CPython 3.14.7; Rush — текущая рабочая
копия, optimized Cargo bench profile. Это начало эксперимента из
[rush-language-landscape.md](rush-language-landscape.md), а не завершённое
сравнение предложенных восьми языков.

## Первая серия: Rush и CPython

### Ручная проверка редактора Rush, 2026-10-01

Проверен текущий Vite dev playground на `127.0.0.1:4180/?lang=rush`
через браузер: UI вызывает Rust bridge через `/api/tokenize` и
`/api/run-rush`. Эта проверка не подтверждает опубликованную WASM-страницу
или качество редакторов остальных семи языков; задержка не измерялась.

- Введено `let angle=degrees(90); 1 < angle`: после анализа показана одна
  диагностика `comparison-operand`, диапазон `27..32`. Клик по диагностике
  выставил выделение textarea `selectionStart=27`, `selectionEnd=32`.
- Введён скрипт с отсутствующим `sum`: запуск показал `Unknown name: sum`
  с позицией `L2:27`; интерфейс вернулся к доступной кнопке Run Rush.
- После замены свёртки на `fold` следующий запуск в той же вкладке дал
  `Number(12.0)` и статус `VALID`:

```rush
let scale = factor => value => value * factor;
[1,2,3] | map(scale(2)) | fold(0, (a,b) => a+b)
```

Просмотрен и сохранён [снимок результата](benchmarks/rush-editor-functional-2026-10-01.jpg).
Это проверка исправления кода после ошибки, замыкания и pipeline через UI.
Она не заменяет проверку отмены, завершения worker или общего лимита памяти.

Production-сборка проверена отдельно через `npm --prefix playground run build:pages`
и Vite preview на `127.0.0.1:4181`. Сборка завершилась успешно. В этом режиме
`runRush` использует WASM в отдельном Web Worker, а не dev bridge.
В той же браузерной вкладке `1/0` показало `Non-finite arithmetic result · L1:1`,
после замены исходника приведённая выше программа дала `Number(12.0)` и `VALID`.
В журнале браузера не обнаружено предупреждений и ошибок. Просмотрен
[снимок WASM-результата](benchmarks/rush-editor-wasm-2026-10-01.jpg).
Проверена локальная production-сборка; публикация сайта и фактическое
освобождение памяти worker этой проверкой не подтверждаются.

## Метод

Использованы существующий `cargo bench --bench runtime` и
[адаптер CPython](benchmarks/python-runtime.py). В каждом случае 10 прогревов,
затем 7 выборок по 100 операций. В таблице медиана в микросекундах на операцию.
Подготовленная программа выполняется в новом окружении при каждом вызове.
Время запуска процесса не входит в эти цифры. Подготовка в Rush строит AST,
в CPython — code object с байткодом; это разные внутренние представления.

Общие задания:

- Замыкание: захват множителя 2 и применение к 21, проверяемый результат 42.
- Eager: 1000 чисел, умножение на 2, отбор кратных 3, свёртка суммы.
- Lazy: то же вычисление с ленивым источником и промежуточными итераторами.

Оба движка используют числа с плавающей точкой. Проверяемая сумма 333666
вычисляется отдельно целочисленным алгоритмом. В Python свёртка использует
`reduce` с lambda, а не оптимизированный `sum`. Eager Python хранит промежуточные
списки в именованных переменных до конца выполнения; Rush передаёт их через
pipeline. Поэтому профиль времени жизни промежуточных объектов различается.

## Результат

| Задание | Rush: подготовка | Python: подготовка | Rush: выполнение | Python: выполнение |
| --- | ---: | ---: | ---: | ---: |
| Замыкание | 2.296 | 15.958 | 3.275 | 0.323 |
| Eager, N=1000 | 3.596 | 33.930 | 370.283 | 95.120 |
| Lazy, N=1000 | 3.484 | 29.119 | 357.424 | 83.578 |

В этой серии подготовка Rush быстрее, а повторное выполнение медленнее.
Это основание исследовать стоимость исполнения и вызовов функций; оно ещё не
доказывает, что переход на байткод будет лучшей следующей оптимизацией.

[Полный вывод Rush](benchmarks/rush-comparison-2026-10-01.txt) и
[полный вывод CPython](benchmarks/python-runtime-2026-10-01.txt) включают min/median/max
и подготовку вместе с исполнением. Строки `surface` в выводе Rush не имеют
Python-аналога и в сравнение не включены.

## Ограничения и незавершённые пункты

Rush считает шаги и проверяет отмену; в этом Python-адаптере эквивалентного
ограничителя нет. Python работает со стандартным GC. Порядок запусков: сначала
Python, затем Rush; чередование, повтор в отдельных сессиях и контроль нагрузки
ещё не выполнены. Одна короткая серия не задаёт устойчивое отношение скоростей.

В этой первой серии не охвачены остальные движки, JSON, объекты хоста, ошибки,
отмена и память. Последующие разделы расширяют покрытие; актуальное состояние
указано в таблице в начале отчёта.
Также остаются холодный старт, пиковая память, качество диагностик, объём
интеграционного кода и работа редактора. Существующие отдельные измерения Rush
не подменяют эти межъязыковые сравнения.

## Rhai 1.26.1: первый прогон

Добавлен [изолированный Cargo-проект](benchmarks/rhai-runtime/Cargo.toml) с
собственным lockfile; зависимости основного workspace не изменены. Включены
default features и стандартная оптимизация Rhai; Engine создаётся один раз вне
замера. Лимит 200000 операций включён, но операция Rhai не равна шагу Rush.
Использованы документированные [замыкания](https://rhai.rs/book/language/fn-closure.html)
и [методы массивов](https://rhai.rs/book/language/arrays.html).

| Задание | Подготовка, мкс | Подготовленное выполнение, мкс | Подготовка + выполнение, мкс |
| --- | ---: | ---: | ---: |
| Замыкание | 4.510 | 0.815 | 5.452 |
| Eager, N=1000 | 7.505 | 830.701 | 750.468 |

Результаты 42 и 333666 проверены до замеров. Ввод коллекции строится в скрипте
через `for` и `push` с преобразованием в float; у Rush для этого встроенный
`range`. Это дополнительное различие стоимости подготовки входных данных.
Ленивый вариант для Rhai пока не реализован.

Серия шумная: prepared-run коллекции имеет диапазон 715.715–2781.561 мкс,
а медиана compile-and-run ниже prepared-run. Поэтому по ней нельзя уверенно
ранжировать движки. [Сырой вывод](benchmarks/rhai-runtime-2026-10-01.txt)
содержит также версии загруженных пакетов и параметры запуска.


Стенд принимает `RUSH_BENCH_ITEMS`, `RUSH_BENCH_ITERS`,
`RUSH_BENCH_CASE=closure|collections|collections_lazy` и
`RUSH_BENCH_OPERATION=compile|prepared_run|compile_and_run`.
Повтор с чередованием описан ниже; расширение общих заданий остаётся в плане.

## Чередование трёх движков

[Runner](benchmarks/compare-runtimes.py) собирает бинарники один раз, затем
запускает их напрямую. Для каждой пары «задание / операция» выполняются три
раунда с порядком Rush/Python/Rhai, Python/Rhai/Rush, Rhai/Rush/Python.
Итого 54 отдельных процесса. Внутри каждого — проверка результата, 10 прогревов
и 7 выборок по 100 операций. Все процессы завершились успешно.

В таблице медиана трёх процессных медиан; скобки показывают их минимум и максимум,

| Задание / операция | Rush | CPython | Rhai |
| --- | ---: | ---: | ---: |
| Замыкание / подготовка | 2.283 (2.279–2.382) | 15.461 (15.262–15.530) | 4.564 (4.487–4.612) |
| Замыкание / выполнение | 3.257 (3.167–3.269) | 0.297 (0.295–0.297) | 0.826 (0.802–0.838) |

[Полные данные](benchmarks/runtime-rotated-2026-10-01.json) содержат порядок,

## Koto 0.16.1 и четыре движка

Добавлен [изолированный стенд Koto](benchmarks/koto-runtime/Cargo.toml) с lockfile.
Используются [compile и run](https://docs.rs/koto/0.16.1/koto/struct.Koto.html),
очистка exports перед каждым выполнением и стандартные настройки. VM создаётся
вне замера. Операция преобразования в установленной версии называется `each`;
её семантика проверена в исходнике `koto_runtime-0.16.1/src/core_lib/iterator.rs`.
Значения источника переводятся к плавающей точке через умножение на 1.0.
У eager явно материализуются промежуточные списки, у lazy сохраняются итераторы.

[Первый отдельный прогон](benchmarks/koto-runtime-2026-10-01.txt) проверил все три
задания, включая lazy. Затем runner выполнил 96 процессов: четыре раунда с
циклическим порядком четырёх движков для замыкания и eager, отдельно для каждой
из трёх операций. Во всех процессах проверены результаты.

Медианы процессных медиан, мкс:

| Задание / операция | Rush | CPython | Rhai | Koto |
| --- | ---: | ---: | ---: | ---: |
| Замыкание / подготовка | 2.332 | 15.908 | 4.644 | 4.229 |
| Замыкание / выполнение | 4.344 | 0.311 | 0.849 | 0.262 |
| Eager / подготовка | 3.692 | 33.504 | 7.734 | 10.014 |
| Eager / выполнение | 379.969 | 94.613 | 732.611 | 314.800 |

[Все 96 результатов](benchmarks/runtime-four-engines-2026-10-01.json) содержат
диапазоны, параметры и stdout каждого процесса. В Python и Koto нет включённого
лимита операций; у Rush и Rhai он есть с разными единицами подсчёта. Koto использует
повторно VM с очищенными exports; Rush создаёт окружение внутри каждого run.
Различия аллокатора, GC и подготовки входа остаются. Это локальный замер рабочих
версий; сравнение с прежними сериями не изолирует изменения Rush от нагрузки
машины и не является отдельным тестом регрессии производительности.

Runner по умолчанию включает шесть движков (Lua и Luau добавлены ниже). Предыдущую тройку можно
выбрать через `--engines Rush CPython Rhai`; число раундов равно числу движков.
Сборка проектов вынесена из измерений. Lua, Luau, Wren и Nushell, а также остальные
задания исходного эксперимента ещё не покрыты.

## Ограничение памяти: Lua и Luau через mlua

[Стенд](benchmarks/lua-memory-limit-shared.rs) устанавливает set_memory_limit
на текущее used_memory + 256 KiB после компиляции. Скрипт пытается сохранить
миллион вложенных таблиц. Оба движка возвращают структурированный MemoryError;
учтённая память в момент возврата не превышает установленный предел.
API и смысл счётчика проверены по исходникам mlua 0.12.1.

| Движок | До запуска, байт | Лимит | После ошибки | После очистки |
| --- | ---: | ---: | ---: | ---: |
| Lua 5.4 | 22966 | 285110 | 285046 | 22337 |
| Luau 0.736 | 452576 | 714720 | 714384 | 403496 |

Для очистки хост временно снимает лимит, освобождает prepared function и дважды
запускает GC, затем восстанавливает исходный предел. В той же VM проверяется
`1+2 == 3` под восстановленным лимитом. [Lua](benchmarks/lua-memory-limit-2026-10-01.txt)
и [Luau](benchmarks/luau-memory-limit-2026-10-01.txt) прошли все проверки.

Это счётчик аллокатора VM, не RSS и не память произвольных функций Rust-хоста.
Пик во время очистки без лимита не измерен. Компиляция в этом сценарии произошла
до включения ограничения; её отказ по памяти пока не проверялся.
Для Rush остаётся отдельная работа: общий учёт живых данных и резервирование
до выделения памяти. Имеющиеся пределы длины каждой коллекции/строки не дают
такого общего ограничения.


## Wren: объект хоста и удаление владельца

[Адаптер](benchmarks/wren-runtime/host-object.c) использует foreign class Point
и один блок управления, принадлежащий C-хосту. Payload с координатой выделяется
хостом отдельно. Два имени Wren указывают на один foreign object: изменение
через point видно при чтении alias, результат равен 5.

Проверены отказ для числового аргумента вместо Point, для другого foreign class
и для строки вместо числового смещения. Бесконечный результат отклоняется до
изменения координаты. Затем хост освобождает payload и обнуляет указатель в
блоке управления: get, move и Host.read через сохранённые имена завершаются
ошибкой `point was deleted`. Та же VM и модуль после ошибок вычисляют 1+2=3.

Это политика владения адаптера: блок управления живёт до уничтожения VM.
Проверка принадлежности foreign object использует идентичность единственного
Point этого стенда; для приложения с множеством объектов потребуется реестр
или другой механизм проверки типа и времени жизни. Wren сам не превращает
сырой указатель хоста в слабую ссылку.

[Результат](benchmarks/wren-host-object-2026-10-01.txt). Сценарий проверяет
поведение; время и память не измеряются.

```sh
/tmp/rush-wren-host-object
```

## Lua и Luau: преобразование JSON-записей

[Общий Rust-хост](benchmarks/lua-records-shared.rs) разбирает JSON через
serde_json 1.0.151, принимает массив длиной до 1000 и проверяет типы всех
строк до фильтрации. Такой же раздел обязанностей используется в примере
Rush: язык получает уже проверенные тройки `(group, amount, active)`.
[Lua-скрипт](benchmarks/lua-records.lua) фильтрует записи, суммирует по строковому
ключу и сохраняет порядок первого появления активной группы. Проверка
переполнения суммы выполняется в скрипте; сериализация результата — в хосте.

Lua 5.4 и Luau 0.736 прошли 16 общих проверок JSON-массивов. Помимо прежних
случаев добавлены пустой ключ и ключ с нулевым байтом, неактивная запись перед
первой активной записью группы, null вместо записи или ключа и числовое поле
active. Ожидаемые результаты заданы независимо от реализации; отрицательные
случаи должны завершаться ненулевым кодом. Rush и Python прошли те же 16
проверок и ещё 8 прежних проверок JSONL.

[Машинный отчёт](benchmarks/json-records-lua-parity-2026-10-01.json) содержит
результаты и stderr. Это проверка корректности: время, память и ограничения
исполнения здесь не сравниваются. В этой серии Lua/Luau-адаптеры буферизовали
весь массив; потоковый режим добавлен следующей серией. Общий Rust-хост означает, что эти результаты не являются
сравнением собственных JSON-парсеров языков.

```sh

python3 docs/benchmarks/compare-json-records.py \
```

### Lua/Luau: потоковый JSONL

Опция `--jsonl` теперь открывает файл через BufReader и передаёт скрипту
callback-итератор. Каждый вызов читает одну физическую строку, разбирает JSON
и проверяет типы записи до передачи в фильтр. Чтение ограничено 65 537 байтами:
строка длиннее 65 536 отклоняется, включая завершающий перевод строки.
Пустой файл допустим, пустая строка и повреждённый UTF-8 — ошибки.

[Новая серия](benchmarks/json-records-lua-stream-parity-2026-10-01.json)
подтвердила все 24 сценария для Rush, Python, Lua и Luau: 16 для массива и 8
для JSONL, включая 10 000 записей, CRLF, последнюю строку без перевода строки
и обе стороны байтовой границы. Отдельный Rust-тест в обоих адаптерах проверяет,
что reader останавливается на границе строки и не потребляет больше 65 537
байт из длинного входа.

Входной поток не собирается в общий массив. Память таблицы итогов растёт с
числом различных активных групп; общего лимита памяти в этом адаптере нет.
BufReader также имеет собственный небольшой буфер чтения. Reader освобождается
при EOF или ошибке чтения/валидации; ошибка в Lua-агрегации возвращается из
run и уничтожает VM вместе с оставшимся callback. Отдельный замер времени
освобождения ресурсов не проводился.

Команда проверки та же, что в предыдущем разделе: переданные Lua/Luau binaries
теперь автоматически участвуют и в JSONL-сценариях.

Для тех же шести JSONL-адаптеров выполнены две серии через macOS time -l:

| --- | ---: | ---: | ---: | ---: |
| Rush | 2.281 | 2.305 | 4.344 | 4.422 |
| CPython | 22.547 | 22.523 | 22.922 | 22.930 |
| Lua | 2.219 | 2.250 | 3.031 | 3.125 |
| Luau | 3.469 | 3.562 | 4.297 | 4.461 |
| Rhai | 3.844 | 3.844 | 5.383 | 5.406 |
| Koto | 7.133 | 7.164 | 8.180 | 8.203 |

При фиксированном числе групп рост числа строк с 1000 до 10 000 мало меняет
RSS этих процессов. Увеличение числа групп повышает RSS: результат группировки
и таблица аккумуляторов требуют памяти даже при потоковом чтении. Это
наблюдение конкретной серии, а не доказательство общего ограничения памяти.
RSS включает весь процесс и его библиотеки; накладные расходы запуска и
представления значений различаются. Время из этих файлов включает обёртку time

Для воспроизведения используйте `measure-json-records.py` с прежними четырьмя
путями `--koto`, `--rhai`, `--lua`, `--luau`, добавив `--rss`. Вторая серия
дополнительно использует `--groups 1000`. Эта опция принимает 1..1000 ключей,
чтобы результат помещался в существующие ограничения Rush-адаптера.

## Wren: JSON/JSONL через Rust-хост

Новый [Rust-хост](benchmarks/wren-records/src/main.rs) разбирает и проверяет JSON
через serde_json 1.0.151. [C-мост](benchmarks/wren-records/bridge.c) передаёт
проверенные тройки в Wren через foreign method и копирует строки по явной длине,
включая нулевой байт. [Скрипт Wren](benchmarks/wren-records/records.wren) выполняет
фильтрацию, группировку и суммирование. Полученный список maps читается через
slot API, после чего Rust сериализует результат. Исходник скрипта фиксирован;
входные строки не подставляются в код.

Контракт соответствует остальным Rust-хостам: массив до 1000 записей, JSONL
по одной строке с пределом 65 536 байт, проверка типов до фильтрации, конечная
сумма и порядок первого активного появления ключа. Встроенный лимит времени
или памяти Wren в этом адаптере не настроен; процесс ограничен timeout стенда.

[Общий отчёт восьми реализаций](benchmarks/json-records-eight-parity-2026-10-01.json):
все восемь прошли 16 сценариев JSON-массива. Rush, CPython, Lua, Luau, Rhai,
Koto и Wren дополнительно прошли 8 сценариев JSONL. Nushell JSONL в стенде пока
не реализован. Время и RSS нового Wren-адаптера ещё не измерены.

Для сборки используется уже проверенный архив Wren 0.4.0, распакованный в
`/tmp/wren-0.4.0`; исходники не скачиваются автоматически. Build script проверяет
версию заголовка при компиляции C, отключает optional meta/random modules и
пересобирает библиотеку при изменении исходников. Точная версия serde_json и
build-зависимостей записана в отдельном Cargo.lock.

```sh
WREN_SOURCE_DIR=/tmp/wren-0.4.0 \
  cargo build --locked --offline --release --manifest-path docs/benchmarks/wren-records/Cargo.toml
WREN_SOURCE_DIR=/tmp/wren-0.4.0 \
  cargo clippy --locked --offline --manifest-path docs/benchmarks/wren-records/Cargo.toml --all-targets -- -D warnings
python3 docs/benchmarks/compare-json-records.py \
  --wren docs/benchmarks/wren-records/target/release/rush-wren-records \
  --output /tmp/json-records-wren-parity.json
```

C-мост прошёл компиляцию с `-Wall -Wextra -Werror`. Дополнительно все 24 случая
прошли с AddressSanitizer для C-моста и Wren:
[отчёт](benchmarks/json-records-wren-casan-2026-10-01.json). Проверяющий скрипт
отдельно отклоняет аварийные коды завершения и сообщения AddressSanitizer, чтобы
сбой памяти на отрицательном входе не считался ожидаемой ошибкой валидации.
Rust-код в этой серии не инструментирован: совместная сборка с Rust ASAN не
связалась из-за несовместимого sanitizer runtime Apple Clang 21. Для C-серии
использовались `CFLAGS=-fsanitize=address` и явное подключение
`libclang_rt.asan_osx_dynamic.dylib` из runtime Apple Clang; результат не следует
считать полной sanitizer-проверкой Rust-части FFI.

## Запуск свежего процесса и минимальной программы

[Стенд](benchmarks/measure-startup.py) отдельно запускает процесс, создаёт движок,
компилирует/исполняет выражение 1+2, проверяет и печатает 3, затем завершает
процесс. Время от subprocess.run до завершения включает загрузку executable,
инициализацию, подготовку, исполнение, вывод и завершение. Сборка исключена.
Это не чистое время инициализации VM и не повторное исполнение в той же VM.

Для Rush, Lua/Luau, Rhai, Koto и Wren используются минимальные compiled hosts.
CPython вызывается с `-I -S -c 'print(1+2)'`: изоляция окружения и отключение
site уменьшают пользовательскую настройку/импорты. Nushell запускается как CLI
с `--no-config-file --no-history -c '1 + 2'`. Стандартные библиотеки и объём
инициализации у этих entrypoints различаются, поэтому интерпретировать таблицу
как чистую стоимость самого языка нельзя.

Первый запуск **внутри серии** сохранён отдельно, затем выполнены 16 раундов
с циклической сменой порядка. Каждый движок занимает каждую позицию дважды;
все 136 запусков вернули 3. Это не первые запуски на машине после установки:
сборки и другие проверки выполнялись ранее. Перед измерением executable читаются
для SHA256; системные кеши не очищаются. Первый запуск не доказывает состояние
холодного файлового кеша. Причины отдельных задержек не профилировались.

## Wren: отказ allocator при ограничении памяти

Добавлен `wren-runtime/memory-limit.c`: собственный `reallocateFn` учитывает
размер каждого живого выделения и возвращает NULL, если новое выделение
превысит лимит. Подготовленный метод создаёт список из 10 000 вложенных списков.
Лимит включается после подготовки и сборки мусора: baseline + 256 КиБ.
Счётчик отражает запрошенные байты VM, исключая служебные заголовки allocator,
память хоста, стек и RSS.

Два отдельных процесса проверены через `check-wren-memory.py` с таймаутом 10 с
и отключёнными core dumps. Сборка Wren 0.4.0 — прежние исходники, `-O3 -DNDEBUG`,
optional meta/random отключены.

| Сценарий | Наблюдение |
| --- | --- |
| Без лимита | Результат 10 000; baseline 126 933 Б, пик 978 213 Б; после wrenFreeVM — 0 Б |
| Лимит 389 077 Б | При live=389 069 Б отклонено расширение с 16 до 32 Б; SIGSEGV, wrenCall не вернулся |
| Тот же лимит, AddressSanitizer | Запись по адресу 0x10 в wrenValueBufferWrite через prim_list_addCore; аварийное завершение |

[Обычная сборка](benchmarks/wren-memory-limit-2026-10-01.json),
[ASAN-сборка](benchmarks/wren-memory-limit-asan-2026-10-01.json).
ASAN подтвердил доступ к нулевой странице, однако внешний symbolizer не смог
дать строки исходника; имена функций присутствуют в трассе. Это воспроизведение
ошибки, а не успешное прохождение проверки безопасности памяти.

В этом сценарии Wren 0.4.0 не превращает отказ allocator в восстанавливаемую
ошибку исполнения. Повторное использование той же VM после отказа невозможно
проверить: процесс аварийно завершился. Поэтому механизм нельзя приравнивать
к проверенному лимиту Lua/Luau с возвратом ошибки и повторным выполнением.
Для данного способа ограничения Wren нужна изоляция процесса либо изменение VM.
Для Rush требование остаётся прежним: общий лимит живой памяти должен давать
контролируемую ошибку, освобождение ресурсов и возможность следующего запуска;
оно пока не реализовано полностью.

Воспроизведение обычной сборки:

```sh
sh docs/benchmarks/wren-runtime/build.sh /tmp/wren-0.4.0 /tmp/rush-wren-memory-limit memory-limit
python3 docs/benchmarks/check-wren-memory.py --binary /tmp/rush-wren-memory-limit --output docs/benchmarks/wren-memory-limit-2026-10-01.json
```


## Wren: остановка изолированного процесса

Проверен `wren-runtime/cancellation.c`: после сигнала о входе в host-функцию
скрипт запускает бесконечный цикл. Во втором режиме host-функция сначала
блокируется в nanosleep на 25 мс. Родитель ждёт маркер и через 5 мс отправляет
SIGKILL только созданному им дочернему процессу. Это механизм изоляции на уровне
ОС; он не реализует кооперативную отмену внутри Wren.

Для каждого режима выполнены три прогрева и 25 измерений. Во всех 56 запусках
код завершения — SIGKILL. После каждого запуска новый процесс вычислил 1+2=3.
Ни в одном из 25 измеряемых запусков с блокирующим хостом не получен маркер
возврата host-функции до завершения процесса.

| Режим | От отправки SIGKILL до обнаружения завершения, min / median / max, мкс |
| --- | ---: |
| Бесконечный скрипт | 1127.875 / 1303.709 / 1319.250 |
| Блокирующий host-вызов | 1066.042 / 1304.958 / 1318.042 |

[Полные результаты](benchmarks/wren-process-cancellation-2026-10-01.json)
содержат фактическую задержку между маркером и запросом для каждого запуска.
Замер включает накладные расходы Python `Popen.wait(timeout=5)` с опросом
завершения, системное планирование и освобождение процесса; он не определяет
точный момент остановки инструкций VM. Эти числа нельзя напрямую сравнивать
с временем возврата кооперативного callback в Lua/Rush/Python.

SIGKILL не вызывает wrenFreeVM, финализаторы объектов или cleanup пользовательского
кода. Память процесса возвращает ОС; побочные эффекты host-вызова не откатываются.
Проверен новый процесс после остановки, повторное использование прежней VM
здесь отсутствует. Публичный заголовок проверенной версии содержит wrenAbortFiber
для текущего fiber; данный стенд не использует его как межпоточный interrupt.

Воспроизведение:

```sh
sh docs/benchmarks/wren-runtime/build.sh /tmp/wren-0.4.0 /tmp/rush-wren-cancellation cancellation
python3 docs/benchmarks/measure-wren-process-cancellation.py --binary /tmp/rush-wren-cancellation --output docs/benchmarks/wren-process-cancellation-2026-10-01.json
```
