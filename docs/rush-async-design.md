# Rush: дизайн async/await (draft)

Дата: 2026-10-25. Ветка `language-improvements`, локальный macOS/aarch64. Это
дизайн-документ; реализация не начата, код не изменён. Все утверждения о
текущем поведении проверены по коду ветки: parser.rs:655-663 и :1265-1272
(`unsupported-syntax` для `async`/`await`), runtime/coroutine.rs,
runtime/scheduler.rs, docs/rush-language-spec.md («Кооперативные корутины»,
«Планировщик времени и событий», «Границы»).

Документ следует выводу docs/rush-language-landscape.md:66: async вводится
вместе с контрактом планировщика и отмены, а не как самостоятельная фича.

## Сводная таблица решений

| Решение | Суть | Обоснование |
| --- | --- | --- |
| `async fn` — сахар над корутиной | Тело исполняется тем же `Coroutine`/`advance`, что и `yield`-функции | Машина уже умеет приостановку, регионы, лимиты, терминальные ошибки (coroutine.rs:101-293) |

## 1. Контекст: что уже есть и проверено

**Корутинная машина.** `ScriptInstance::spawn_coroutine` регистрирует
именованную функцию как задачу, не исполняя тело (coroutine.rs:316-407):
проверяются арность и аннотации параметров, собирается окружение с
sibling-функциями и самоссылкой, создаётся `Coroutine { frames, regions }`.
`resume_coroutine` исполняет до `yield`/возврата со свежими лимитами; при
возврате проверяется аннотация результата (`Return value does not match its
type annotation`, coroutine.rs:447-463). Локали, захваты, позиции ветвей/циклов
и открытые итераторы сохраняются между шагами; региональные кадры паркуются
в `task.regions` на время приостановки и восстанавливаются при возобновлении
(coroutine.rs:426-445). Ошибка в шаге терминальна: задача удаляется, мутации
сохраняются (`cancel_coroutine`, coroutine.rs:493-498).

**Планировщик.** `CoroutineScheduler` (scheduler.rs:33-212) — детерминированный,
host-driven: `spawn` регистрирует готовую задачу, `poll(now, limits)` продвигает
монотонное время и делает максимум один шаг на задачу за вызов (защита от
голодания при нулевой задержке, scheduler.rs:143-145), `emit(name)` будит всех
текущих подписчиков в порядке создания без payload и без буферизации,
`next_deadline` помогает хосту выбрать момент следующего `poll`. Запрос
пробуждения декодируется из yield-значения `Wait.After(number)` /
`Wait.Event(str)` (scheduler.rs:128-142); невалидный запрос завершает задачу
ошибкой. Планировщик не спит, не создаёт потоков, не делает I/O; Drop отменяет
все задачи. `OwnedCoroutineScheduler` (scheduler.rs:216-305) даёт ту же
семантику без заимствования инстанса — готовая форма для браузерных и
прикладных handle'ов.

**Контракты, которые дизайн обязан сохранить** (спека):

- Значение `yield` непрозрачно для ядра; ядро не ждёт часы, не запускает
  потоки, не создаёт подписки (спека :651-655).
- Липкая отмена: следующий `spawn`/`resume` после установки токена освобождает
  все задачи и возвращает `Execution cancelled` (спека :661-662,
  coroutine.rs:309-312, scheduler.rs:121-127).
- `?` в задаче возвращает обычный `None`/`Err`; ошибки, отмена и исчерпание
  бюджета — ошибки API (спека :667-668).
- Сохранённые окружения и источники учитываются в retained-data budget
  (спека :669-670).
- `max_heap_bytes` / `max_allocated_bytes` следуют per-call `ExecutionLimits`;
  в корутине исчерпание терминально для задачи, остальные продолжаются
  (спека :271-298; docs/rush-memory-limit-design.md, сводная таблица).

## 2. Синтаксис

```rush
enum Wait { After(number), Event(str) }   // уже существует у хостов-пользователей планировщика

async fn load(name: str) -> Result[Record, str] {
  await Wait.Event("io:ready")
  let data = fetch(name)?      // обычный синхронный вызов; ? — как сегодня
  return Ok(data)
}

async fn main_task() -> number {
  await Wait.After(0.25)
  let result = await load("a") // вложение задачи, §2.3
  return 1
}
```

### 2.1. `async fn`

- Маркер `async` перед `fn`; разбирается в `Parser::statement` до ветки
  `"fn"` (сейчас перехват на parser.rs:655-663) и в `Parser::function`.
- AST: флаг на существующем `StmtKind::Function { .. }` (`is_async: bool`),
  а не новый вариант — тогда анализ, форматтер, хойстинг и интерфейсы модулей
  получают async-функции бесплатно, с одной проверкой флага там, где семантика
  вызова отличается.
- Аннотации параметров и результата — те же, проверки при spawn и возврате —
  те же, что у корутин сегодня (coroutine.rs:336-345, :447-463). В strict-
  режиме `async fn` подчиняется `compile_strict` без исключений: аннотация
  результата описывает **итоговое значение задачи**, а не handle.

### 2.2. `await expr`

- Новое префиксное выражение `ExprKind::Await(Box<Expr>)` в primary-позиции
  (сейчас перехват на parser.rs:1265-1272). Приоритет — как у унарных
  операторов; `await` не является выражением-оператором.
- **Статическое правило:** `await` допустим только в теле `async fn`
  (лексически — не учитывая вложенные обычные `fn`/замыкания, по образцу того,
  как вложенные функции не переносят `yield` и возвраты). Нарушение —
  диагностика `await-outside-async` «await requires an async function body»
  при разборе. Это зеркалит существующее `yield-outside-body` и сохраняет
  свойство «ошибка грамматики, а не runtime-сюрприз».
- Значение операнда решает семантику (§3).

### 2.3. Async-замыкания

Вне минимального среза. `spawn_coroutine` сегодня требует имени и именованного
тела (coroutine.rs:321-335); анонимная async-задача потребовала бы либо
синтетических имён, либо нового пути спауна по значению-замыканию. Отдельный
дизайн-вопрос, стадия C (§6). Форма `async =>` в стадии A отклоняется той же
диагностикой `unsupported-syntax`.

## 3. Семантика

### 3.1. Вызов `async fn` возвращает задачу (handle)

`let t = load("a")` **не исполняет тело**. Выражение-вызов async-функции
создаёт задачу в том же инстансе и возвращает значение `Value::Task(CoroutineId)`
— непрозрачный handle, по аналогии с тем, как `spawn` возвращает `CoroutineId`
хосту. Это прямое продолжение модели «задача принадлежит планировщику/хосту»:
ядро не создаёт исполнения без точки приостановки.

Решено (§7, вопрос 1): созданная задача «не запланирована», пока её не
`await`-нут или хост не передаст в планировщик явно. Задача существует в
`runtime.coroutines`, а планировщик подхватывает её при явной регистрации
или при `await` (§3.3). Это не меняет устройство `CoroutineScheduler`.

### 3.2. `await Wait.After(...)` / `await Wait.Event(...)`

Маппинг один-в-один на существующий протокол: выполнение операнда даёт значение
`Wait`, задача приостанавливается с `CoroutineState::Yielded(wait)` — ровно то,
что сегодня делает `yield Wait.After(0.25)`. Планировщик декодирует запрос
тем же `Scheduler::request` (scheduler.rs:128-142) без изменений: таймер,
подписка, валидация длительности, терминальная ошибка при невалидном значении.
`await` после пробуждения возвращает `null` (события payload не несут — спека
:747-748; менять это — отдельное решение, см. §7, вопрос 2).

### 3.3. `await <task-handle>` — вложение задач

`await t`, где `t: Value::Task`, приостанавливает текущую задачу до завершения
`t` и возвращает итоговое значение `t`. Механизм — новый вариант запроса
пробуждения `WakeRequest::Task(CoroutineId)` (scheduler.rs:6-9) с семантикой:
задача-ожидальщик становится готовой, когда целевая задача дошла до
`Complete`/`Failed`. `Failed` целевой задачи — терминальная ошибка ожидающей
(ошибки задач терминальны, спека :742-743), либо — альтернатива на выбор —
передаётся как `Err`-значение, если целевая функция аннотирована `Result`
(см. §7, вопрос 3). Циклы ожидания (`a` ждёт `b`, `b` ждёт `a`) детектируются
планировщиком при регистрации ожидания: обе задачи завершаются ошибкой
«Cyclic task await», а не висят — детерминизм планировщика сохраняется.

Вложение **не** меняет правило спеки :665-666 «вложенный вызов обычной функции
не может пересечь yield»: обычные `fn`, вызванные из async-тела, по-прежнему
синхронны и не содержат `await` (проверяется статически §2.2).

### 3.4. Отношение к `yield`

`async fn` — сахар над корутиной: компиляция тела идёт в тот же `Coroutine`/
`Frame`/`advance`. `yield` внутри `async fn` допустим и эквивалентен
`await <того же значения>` для `Wait`-запросов; смешивание не запрещается,
но дизайн не поощряет: `yield` остаётся низкоуровневой формой для хостов с
собственными протоколами, `await` — типизированной формой с контрактом
планировщика. Обратное неверно: обычная `fn` с `yield` не становится
async-задачей и не получает `await`.

## 4. Отмена и ошибки

Без новых механизмов — дизайн наследует и фиксирует существующие контракты:

- **Липкая отмена.** Общий `CancellationToken` остаётся единственным источником
  глобальной отмены; поведение `poll`/`spawn`/`resume` при установленном
  токене — как в scheduler.rs:121-127 и спека :752-754. Новый путь `await`
  обязан проходить те же проверки `check_cancelled`.
- **Отмена одной задачи.** `cancel`/`cancel_coroutine` немедленно освобождают
  локали и итераторы, мутации сохраняются (спека :657-660). Если отменённую
  задачу кто-то `await`-ит, ожидающая задача получает терминальную ошибку
  «Awaited task was cancelled» — висячих ожиданий быть не должно.
- **Ошибки.** RuntimeError в async-шаге терминальна для задачи; планировщик
  возвращает `ScheduledState::Failed`, остальные готовые задачи продолжаются.
  `?` остаётся обычным `None`/`Err`-возвратом из задачи (спека :667-668);
  `await` успешно завершённой задачи с `Err(...)`-значением — это значение,
  а не ошибка API (propagation делает сам скрипт через `?`).
- **Аннотация результата.** Проверяется на итоговом значении при `Complete`,
  как сегодня (coroutine.rs:447-463); `async fn load(...) -> Record` гарантирует,
  что `await` handle'а даёт `Record` или задача завершилась ошибкой.

## 5. Лимиты

- **Шаги и глубина** применяются per-resume через существующий
  `coroutine_limits` (coroutine.rs:296-314): каждый `await` делит задачу на
  шаги, каждый шаг получает свежие `ExecutionLimits` от `poll`/`resume`.
  Лимит глубины ≤ 64 неизменен; кадры async-задачи — те же `Frame`, тот же
  счётчик.
- **Память.** `max_heap_bytes` (пик) и `max_allocated_bytes` (кумулятивная
  работа) действуют на async-задачи ровно как на корутины: исчерпание
  терминально для задачи (`Heap limit exceeded` / `Allocation limit exceeded`),
  остальные задачи инстанса продолжаются, инстанс остаётся пригодным
  (спека :275-279). Резервации кадров и паркованных регионов уже покрыты
  журналом; `enforce_memory_limit` на границах spawn/resume
  (coroutine.rs:401-405, :482-486) покрывает и новые handle-задачи, поскольку
  они живут в том же `runtime.coroutines`.
- **Retained-data budget.** Сохранённые окружения/захваты async-задач
  учитываются в retained-бюджете инстанса, как для корутин (спека :669-670).
  Ожидания/подписки/таймеры — собственность хоста и планировщика, в бюджет
  скрипта не входят (спека :755-756); `Value::Task` — непрозрачный id,
  а не данные, поэтому его учёт минимален (размер слота `Value`).
- **Что лимиты не покрывают** (наследуется, не новое): аллокации хост-колбэков,
  оверхед аллокатора, время настенных часов — планировщик времени не ждёт.

## 6. Явно вне объёма

- **Настоящий параллелизм и потоки.** Кооперативная однопоточная модель —
  осознанная граница: «ядро не ждёт настенные часы, не запускает потоки»
  (спека :653-655). `async`/`await` это не меняют.
- **I/O.** Сокеты, файлы, таймеры реального времени — обязанность хоста;
  скрипт выражает ожидание только через `Wait.After`/`Wait.Event` и события
  без payload.
- **Futures/промисы как экосистема.** Нет `Future`-трейта, комбинаторов
  (`join`/`select`/`race`), executor-абстракций внутри скрипта. Единственный
  executor — существующий `CoroutineScheduler`. Комбинаторы уровня «дождаться
  двух задач» выражаются последовательными `await` или хостовым кодом.
- **Async-замыкания, async-методы структур** — до отдельного решения (стадия C).
- **Сериализация состояния задач** (`StateValue` и т.п.) — задачи несериализуемы,
  как и сегодня корутины.
- **Bytecode VM.** Стадия A — только tree-walk runtime; покрытие VM
  async-формами — отдельный этап с собственными тестами (по образцу
  «Bytecode VM делит тот же журнал», спека :282-284).

## 7. Решённые вопросы (выбор сделан 2026-10-25, до реализации стадии A)

1. **Регистрация handle-задач в планировщике — явная.** Задача существует в
   `runtime.coroutines`; планировщик подхватывает её при явной регистрации
   хостом (`spawn_task`) или при `await`. Направление зависимости
   «scheduler заимствует instance» не меняется; автоматическая регистрация
   при создании отклонена.
2. **Payload событий — отложен за стадию A.** Контракт планировщика не
   меняется: `emit(name)` без данных, `await Wait.Event(...)` возвращает
   `null`. Расширение — отдельное решение стадии C.
3. **Ошибка ожидаемой задачи при `await task` — терминальная для ожидающего.**
   Доставка как `Err`-значения отклонена: два канала ошибок спеки :667-668
   остаются разведёнными.
4. **Диагностика для `await` в обычной функции — свой код
   `await-outside-async`**, симметрично `yield-outside-body`.
5. **Редакторские подсказки результата `await` — стадия B.** На стадии A
   минимум: отдельное имя типа `task` в `typeof`/`repr`.

## 8. План реализации по стадиям

По образцу stage-модели rush-lang: каждая стадия — самостоятельный зелёный
срез с тестами, спекой и гейтами.

**Стадия A — минимальный честный срез: `async fn` + `await Wait`.**
- Парсер: `async fn` (флаг на `StmtKind::Function`), `ExprKind::Await`,
  диагностика `await-outside-async`; `async`/`await`/`import` перестают
  попадать под общий перехват только для реализованных форм.
- Runtime: вызов async-функции создаёт задачу и возвращает `Value::Task`;
  `await Wait.*` компилируется в тот же `Yield`-путь `Coroutine::advance`.
- Без вложения задач (`await task` — ошибка «Task await is not supported at
  this stage» на этой стадии) и без async-замыканий.
- Критерии готовности: новые тесты в `tests/coroutines.rs`/`tests/scheduler.rs`
  (spawn async fn через планировщик, таймер, событие, терминальная ошибка,
  отмена, лимиты 2b/2c посреди await-цикла); тесты парсера на диагностики
  (вне async, во вложенной обычной fn); спека обновлена (разделы «Кооперативные
  корутины», «Планировщик», «Границы» — снять строку :764-765); форматтер
  сохраняет `async`/`await` (tests/formatter.rs); `cargo test -p
  themoretheless-tokenizer-rush` и гейты `tests/wiring_completeness.rs`
  зелёные.

**Стадия B — вложение задач и редакторский анализ.**
- `WakeRequest::Task`, детекция циклов ожидания, `await task` с проверкой
  аннотации результата целевой функции анализатором.
- Критерии: тесты на вложение, отмену ожидаемой задачи, циклы; спека
  (вложение, ошибки); редакторские дополнения результата `await` — если
  выбраны на стадию B (§7, вопрос 5); все гейты зелёные.

**Стадия C — расширения по решению:** async-замыкания, payload событий,
покрытие bytecode VM. Каждый пункт — отдельный дизайн-абзац в спеке и свой
тест-набор; в минимальный драфт не входят.

## 9. Риски

1. **Спека про планировщик.** Вложение задач (стадия B) — первое изменение
   протокола `WakeRequest` со времён его фиксации; риск рассинхронизации
   спека↔код снимается тестами scheduler.rs на каждую новую ветку `Waiting`.
2. **Retained-data budget.** `Value::Task` удерживает задачу живой; если
   handle переживает отмену планировщика, освобождение обязано оставаться
   за `cancel_coroutine`/Drop инстанса — нужен тест «handle после cancel_all»
   (риск утечки корутинных кадров вне учёта).
3. **Редакторский анализ.** Анализ `missing-return` и полные контракты
   (спека :316-328, :695-703) должны трактовать async-тело как обычное:
   флаг `is_async` не отключает структурный анализ путей возврата. Риск —
   ложные/пропущенные диагностики, если ветвление по флагу забудет путь;
   снимается тестами analysis на async fn с аннотацией результата.
4. **`?` + `await` в одном выражении.** Порядок операций (`(await t)?` против
   `await (t?)`) обязан быть зафиксирован приоритетом §2.2 и покрыт тестами
   try_operator.rs — иначе тихая смена семантики propagation.
5. **Совместимость перехвата.** Снятие общего перехвата parser.rs:655-663 /
   :1265-1272 меняет диагностику существующих программ, упоминающих
   `async`/`await`: сообщение обязано остаться `unsupported-syntax`-семейства
   для нереализованных форм, чтобы хосты, фильтрующие по коду, не сломались.
6. **Производительность.** Стадия A не добавляет работы на горячие пути
   обычных функций: проверка флага `is_async` — одно сравнение на вызов.
   Подтвердить бенчем `runtime` по методике docs/rush-performance.md при
   реализации (критерий — как в memory-limit драфте: в пределах устойчивости
   методики, >5% требует объяснения).
