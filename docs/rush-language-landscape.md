# Rush и 100 языков для сравнения

Дата исследования: 30 сентября 2026 года.

## Главный вывод

Моя рекомендация: развивать Rush как встраиваемый язык для преобразования данных и управления объектами приложения. Его ближайшие ориентиры — Rhai и Koto для интеграции с Rust, Lua и Wren для устройства небольшого движка, Luau для анализа и ограничений исполнения, Nushell и jq для данных, GDScript для связи языка с редактором.

Это предложение по результатам обзора, а не доказательство превосходства будущего Rush. Чтобы проверить его, нужны исполняемые примеры и одинаковые задания для Rush и выбранных альтернатив.

## Метод и границы исследования

Рассмотрены 100 отдельных языков или существенно отличающихся диалектов. Включены прямые альтернативы для встраивания, универсальные скриптовые языки, shell, языки конфигурации и предметные языки. Kotlin, Scala, C#, Haxe и некоторые другие участники шире понятия «скриптовый язык»; они включены как смежные решения. Номер строки — идентификатор, а не место в рейтинге.

Основа — документация, спецификации и репозитории авторов. Для каждого участника ниже есть ссылка на первичный источник, конкретное наблюдение и отдельный вывод для Rush. Три страницы GNU не удалось открыть напрямую; для Bash, awk и Emacs Lisp использован доступный поисковый текст официальных руководств. Для остальных участников прочитана доступная страница документации, описание проекта или README; это обзор архитектурных решений, а не построчное изучение всех реализаций.

Я не устанавливал и не измерял все 100 движков. Скорость, расход памяти, качество sandbox и зрелость сопровождения не ранжируются. Рекламные заявления авторов о производительности не считаются результатами независимых измерений. Lua и Luau, Python и Starlark учитываются отдельно из-за различий языка; Node.js, Deno, Bun, LuaJIT и CPython не посчитаны дополнительными языками.

На момент исходного обзора Rush имел lexer, parser, собственный AST и частичную проверку объявлений. С тех пор добавлены исполнение и анализ; актуальное состояние и оставшиеся ограничения приведены в разделе «Состояние реализации после функционального и графического прототипа» ниже и в [спецификации](rush-language-spec.md). Рекомендации обзора описывают план развития, а не перечень уже реализованных возможностей.

## Что меняется в плане Rush

### Сначала назначение и три программы

Предлагаю проверять Rush на трёх задачах:

1. Преобразование списка записей: фильтрация, отображение, группировка и сериализация.
2. Вызовы API приложения: создать объект, изменить параметр, получить видимый результат.
3. Пакетная автоматизация: прочитать разрешённые входы, обработать ошибки, отменить выполнение.

Для геометрического приложения второй сценарий — параметрическая модель; для другого хоста он заменяется его реальными объектами. Это гипотеза назначения, а не зафиксированное требование пользователя.

Сравнение этих задач с Rhai, Koto и Lua покажет, что именно Rush упрощает. Если преимущество не проявится, следует пересмотреть объём собственного runtime, а не наращивать грамматику автоматически.

### Pipeline нужно определить до исполнителя

Символ pipe скрывает разные модели:

| Модель | Пример ориентира | Что передаётся | Следствие для Rush |
| --- | --- | --- | --- |
| Связь процессов | Bash | Данные через стандартные потоки | Нужны процессы, коды завершения и правила преобразования данных |
| Поток объектов | PowerShell, Nushell | Объекты или значения с типами | Нужны stream, сбор результата и обработка ошибок по этапам |
| Композиция фильтров | jq | Ноль, одно или несколько выходных значений | Один этап способен умножить количество результатов |
| Композиция вызовов | Elixir | Значение передаётся в следующий вызов | Можно начать с простого преобразования вызова функции |

Источники: [Bash](https://www.gnu.org/software/bash/manual/html_node/Pipelines), [PowerShell](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_pipelines), [Nushell](https://www.nushell.sh/book/pipelines.html), [jq](https://jqlang.org/manual/), [Elixir Kernel](https://elixir.hexdocs.pm/Kernel.html).

Мой выбор для первой версии Rush: `x | f(a)` означает `f(x, a)`; левая часть вычисляется ровно один раз. Список остаётся одним значением. Поэлементное вычисление задаётся явно через `map`/`filter`. Поток и внешние процессы — последующие явные расширения. Это правило отличается от потоковой модели jq и не должно документироваться как её эквивалент.

`where size > 100` пока не стоит превращать в особую магию разрешения имён. Сначала нужна обычная функция-предикат, затем можно решить, окупается ли сокращение с неявной текущей записью.

### Типы и ошибки раньше, чем в предыдущем плане

Luau демонстрирует пользу анализа для редактора, GDScript связывает типы с объектами приложения, Nickel и Pkl показывают проверки контрактов и подробные ошибки. Вывод для Rush: уже при первом host API нужны описание сигнатур, проверка аргументов и результата, а также сообщения с исходными позициями. Полные generics и сложный вывод типов можно отложить. [Luau](https://luau.org/types/), [GDScript](https://docs.godotengine.org/en/stable/tutorials/scripting/gdscript/gdscript_basics.html), [Nickel](https://nickel-lang.org/user-manual/contracts/), [Pkl](https://pkl-lang.org/).

Нужно отдельно решить поведение отсутствующего ключа, null, деления на ноль, переполнения, ошибки host-функции и отмены. Нельзя автоматически представлять все эти случаи одним null: пользователь потеряет причину и место сбоя. Это моя рекомендация для Rush.

### Ограничения исполнения входят в первый runtime

Rhai документирует ограничения ресурсов. Luau предоставляет прерывания, но отмечает, что долгая native-функция может задержать остановку. Поэтому лимит шагов интерпретатора Rush не будет ограничением времени выполнения произвольной функции хоста. API должен отдельно описывать отмену, блокирующие вызовы и выделение памяти вне runtime. [Rhai](https://rhai.rs/book/safety/index.html), [Luau](https://luau.org/sandbox/).

Для первой версии предлагаю отдельные лимиты на шаги, глубину вызовов и размер данных; явную отмену; доступ к файлам, сети и процессам только через зарегистрированные возможности приложения. Это проектное требование, не утверждение о существующей изоляции Rush.

### Редактор следует развивать вместе с исполнением

Предлагаю один каталог функций и типов хоста для анализатора, исполнения, автодополнения и документации. Это должно уменьшить расхождения между подсказкой и реальным вызовом. Проверка — тест, который для каждой зарегистрированной функции сверяет сигнатуру редактора и runtime. Полезные ориентиры: [Rhai](https://rhai.rs/book/rust/functions.html), [GDScript](https://docs.godotengine.org/en/stable/tutorials/scripting/gdscript/gdscript_basics.html), [Nushell](https://www.nushell.sh/book/pipelines.html).

## Решения, которые надо записать до расширения грамматики

- Являются ли `x` и `$x` разными именами. Текущее написание `.r`, комментарии `//` и `return` сохранить по выбору пользователя.
- Как объявление функции связано с порядком инициализации переменных; что захватывает замыкание.
- Защищает ли `const` только имя или также содержимое; что происходит с алиасами коллекции.
- Как представлены целые числа и дроби; что делают смешанные операции и переполнение.
- Какая запись блока и вызова считается канонической для форматтера при сохранении совместимости.
- Что возвращают отсутствующий ключ и функция без return; как обрабатываются ошибки.
- Какая форма передачи аргумента через pipe является нормативной.
- Как устроены identity и lifetime объектов хоста; что происходит после удаления такого объекта в приложении.
- Как разрешаются импорты, фиксируются зависимости и диагностируются циклы модулей.
- Что гарантируют аннотации типов при анализе и при исполнении.

## Как проверить конкурентоспособность

Следующий эксперимент стоит проводить на 6–8 ближайших альтернативах, а не сразу на всех 100. Предлагаемый набор: Rhai, Koto, Lua, Luau, Wren, Nushell, Python и Rush. Для shell-задач и встраивания нужны разные группы результатов.

Одинаковые задания: преобразовать JSON-записи; вызвать функцию приложения с пользовательским типом; замкнуть переменную; обработать ошибку; остановить бесконечный цикл; повторно исполнить подготовленный скрипт. Для каждого фиксировать:

- Число строк скрипта и кода интеграции, отдельно.
- Качество ошибки: исходная строка, диапазон, ожидаемое и полученное значение.
- Холодный старт, разбор/подготовку и повторное выполнение, отдельно.
- Пиковую память и поведение при ограничениях; версию, конфигурацию и платформу.
- Время реакции на отмену отдельно для чистого скрипта и native-вызова.
- Путь от изменения кода до результата в редакторе.

Первый замер Rush и CPython для замыканий и eager/lazy-коллекций описан в [отдельном отчёте](rush-competitor-measurements.md). В отчёте есть серия с чередованием семи движков, отдельная shell-серия Nushell, JSON, объекты хоста и проверки остановки для части движков. Таблица покрытия перечисляет оставшиеся сценарии; полный эксперимент не завершён.

## Итоговая рекомендация

На ближайший этап взять: контракт значений и ошибок, ясное правило pipe, реальные функции хоста, небольшой исполнитель, лимиты и диагностику. Затем добавить полное разрешение имён и удобства редактора. Макросы, пользовательские операторы, классы с наследованием, распределённые акторы, полную shell-совместимость и JIT отложить до сценария, который их требует.

Главная проверяемая гипотеза: Rush позволит описывать преобразования данных и действия приложения коротко, а редактор сможет объяснять ошибки и показывать результат через тот же API, которым пользуется исполнитель.

Статический playground выполняет Rush в отдельном Web Worker с отменой и
тайм-аутом. Проверки редактора пока выполняются отдельно от этого worker.
В dev-режиме отмена запроса завершает отдельную группу процессов на macOS/Linux.
На Windows используется `taskkill /T /F`; проверка завершения потомков включена
и для Windows, но запуск на Windows ещё не подтверждён.

После уточнения пользователя 3D-просмотр убран из playground токенизатора.
Визуализация относится к приложениям-хостам. Ближайшие незакрытые направления
языка: общий лимит памяти и полнота статических контрактов. Дополнение известных
полей работает после имён, вызовов, скобок и литеральной индексации;
вычисляемые ключи и неизвестные результаты остаются без предположений.
Контракт времени жизни объектов хоста реализован и проверяется примером
`host_scene`; интеграция с конкретным приложением остаётся отдельной задачей.
После профилирования выполнен ограниченный эксперимент AST/инструкций:
скалярная арифметика, ветвления, scalar host-вызовы и неизменяемые захваты,
включая подготовку и память. Результаты в отчёте производительности;
преимущества смены рабочего исполнителя на реальных задачах пока не доказаны.

### Границы ограничений данных

`ExecutionLimits` и CLI (`--steps`, `--depth`, `--items`, `--string-bytes`)
позволяют ограничить работу интерпретатора и размер отдельных создаваемых
значений. Коллекции проверяются при создании литералов, eager-преобразованиях,
`collect` и построении геометрии; строки — при декодировании литералов и
конкатенации, а также имена полей записей. Тесты `limits.rs`, `host_sequences.rs` и `cli.rs` проверяют границы,
ошибки и передачу параметров в тестовые скрипты.

Это ещё не общий лимит памяти: много допустимых значений могут одновременно
занимать большой объём. Результаты функций хоста и элементы host-потоков
проверяются рекурсивно после получения; обход расходует бюджет шагов и
ограничивает глубину данных числом 64. Ошибка закрывает открытый источник
без чтения следующего элемента. Ёмкость аллокатора, скрытое состояние
opaque-объектов и память внутри native-вызовов требуют отдельного учёта.
Измеренное удержание RSS после освобождения значений описано в
[rush-performance.md](rush-performance.md): эксперимент с `MallocLargeCache`
показал влияние кеша malloc на macOS, но не ограничивает пик живой памяти.

Локальные изменяемые переменные больше не требуют новой постоянно занятой
ячейки на каждой итерации: binding и захват замыкания удерживают идентификатор
ячейки. После исчезновения последнего такого владельца ячейка попадает в
очередь; при выходе из блока, функции или модуля, а также перед созданием `mut`
её значение освобождается, а слот может использоваться повторно.
Освобождение захваченных ячеек обрабатывается
каскадно. Тест `cell_lifetime.rs` проверяет 1000 итераций и вызовов функций,
сохранность вышедшего из функции замыкания и освобождение при завершении run.
Дополнительно runtime периодически собирает недостижимые циклы ячеек:
учитывает ссылки внутри замыканий, окружений, записей, коллекций и ленивых
последовательностей. Ссылки извне этого графа считаются корнями, включая
активные вызовы и значения, сохранённые хостом. Обход расходует бюджет шагов
и проверяет отмену. Интервал начинается с 64 созданий ячеек и зависит от
числа ячеек, оставшихся живыми после предыдущего обхода.
Очередь очищается на указанных границах, а не после каждого выражения;
ёмкость массива слотов не уменьшается. Внутренности opaque-объектов хоста
не обходятся. Общий лимит памяти по-прежнему не реализован.

Первый шаг к общему учёту находится в `runtime/memory.rs`: прототип резерва
байтов с общим счётчиком, проверкой переполнения, атомарным отказом при
превышении и освобождением через `Drop`. Резерв и типизированный массив уже
используются рабочим runtime для слотов изменяемых переменных и массива их
слабых идентификаторов. Оба массива используют общий счётчик. Их ёмкость
резервируется до добавления элементов, поэтому отказ роста одного массива
не нарушает соответствие индексов. Пока их бюджет
равен `usize::MAX`; публичного лимита ещё нет, а вложенные `Value` используют
старое хранилище. Отказ аллокатора при росте ячеек возвращает `RuntimeError`;
следующий вызов экземпляра сохраняет доступ к ранее созданным переменным.
Следующая необходимая работа — связать резерв со всеми остальными выделениями:

- Перевести строки, списки, записи, варианты и геометрию на внутреннее
  хранилище с резервом; общий `Rc` должен удерживать один резерв, глубокая
  копия — получать новый до выделения.
- Учесть ёмкость временных буферов, окружения, содержимое ячеек, замыкания и кеши модулей.
  При росте резервировать новую ёмкость до выделения; при отказе аллокатора
  восстанавливать резерв, не теряя старое значение.
- Отделить публичный `Value` хоста от управляемого внутреннего значения.
  При импорте проверять и учитывать данные; произвольные выделения внутри
  callback остаются ответственностью хоста.
- Проверить превышение суммарного лимита несколькими допустимыми по отдельности
  значениями, временные копии, циклы, возвращённые наружу значения и память,
  сохранённую между `ScriptInstance::call`. Только затем открывать лимит в API.

Прототип теперь включает байтовый буфер с точным размером выделения:
резерв получается до обращения к аллокатору, глубокая копия резервируется
отдельно, рост учитывает одновременно старый и новый буферы. Отказ сохраняет
исходное содержимое. Пять тестов проверяют эти границы, переполнение и
освобождение. Буфер использует небольшой изолированный участок `unsafe`
для fallible allocation с известным `Layout`; результаты AddressSanitizer и
Miri приведены ниже. Производственные
значения пока используют прежнее хранилище.
В этом же прототипе добавлен типизированный массив: резервируется вся ёмкость
с учётом выравнивания, при росте элементы перемещаются без глубокого копирования,
освобождается только инициализированный префикс. Восемь тестов механизма памяти
теперь включают вложенные буферы, отказ роста, выравнивание 64 байта, элементы
нулевого размера и освобождение резерва при панике деструктора элемента.
Массив ещё не подключён к `Value::List` или окружениям runtime.
Добавлен перенос обычных данных `Value` в управляемое представление: числа,
углы, bool/null, строки, векторы, списки, кортежи, варианты и записи с ключами.
Тест использует реальный результат исполнения Rush, проверяет точную границу
общего бюджета и освобождение частично построенной записи при отказе.
Глубина переноса ограничена 64; исполняемые значения пока явно отклоняются.
Также переносятся матрицы, кватернионы, точки полигонов, вершины и индексы mesh.
Для каждой геометрической формы тест проверяет точный размер выделения;
отказ выделения индексов mesh освобождает уже перенесённые вершины.
При импорте mesh копируется в новый бюджет, а не заимствует исходный `Rc`.
Одиннадцать тестов проходят. Этот перенос остаётся прототипом, а не частью исполнения.
Перенос дополнительно принимает бюджет шагов и cancellation token: расходует
шаг на узел, байт строки/ключа и элемент геометрического массива. Копирование
строк проверяет отмену между блоками по 4096 байт, геометрия — между элементами.
Двенадцатый тест проверяет все недостаточные бюджеты короткой вложенной
коллекции, точную достаточную границу, отмену до переноса и отсутствие
оставшихся резервов после отказа. Вызов системного аллокатора сам по себе
не прерывается token; его размер ограничивается резервом памяти.
Управляемые данные теперь копируются через fallible `try_copy`, без временного
публичного `Value`: вложенные данные и геометрия резервируются в целевом
бюджете до выделения. Три недостаточные границы проверены на составной
записи: источник сохраняется, частичная копия освобождается. При достаточном
бюджете копия переживает удаление источника и освобождает собственный резерв.
Это тринадцатый тест прототипа; обычный runtime `Clone` ещё не заменён.

Эти 13 тестов также прошли под AddressSanitizer на macOS arm64,
`rustc 1.101.0-nightly (c1070d693 2026-09-28)`. Команда:

```sh
RUSTFLAGS='-Zsanitizer=address' CARGO_TARGET_DIR=/tmp/rush-managed-memory-asan \
  cargo test --locked -p themoretheless-tokenizer-rush \
  --target aarch64-apple-darwin --lib runtime::memory -- --test-threads=1
```

[Вывод sanitizer](benchmarks/rush-managed-memory-asan-2026-10-01.txt) не содержит
сообщений об ошибках памяти. Это проверка покрытых путей прототипа; она не
заменяет полный аудит `unsafe` и интеграцию с рабочим runtime.

Те же 13 тестов прошли под Miri со строгой проверкой происхождения указателей
(`-Zmiri-strict-provenance`), включая рост массивов, значения нулевого размера
и панику деструктора. [Полный вывод](benchmarks/rush-managed-memory-miri-2026-10-01.txt).
Для существующего nightly установлены официальные компоненты `miri` и `rust-src`.
В этой среде запуск через `cargo miri` не находил установленный компонент;
проверка выполнена напрямую:

```sh
CARGO_TARGET_DIR=/tmp/rush-managed-memory-miri MIRIFLAGS='-Zmiri-strict-provenance' \
  rustup run nightly cargo-miri miri test --locked \
  -p themoretheless-tokenizer-rush --lib runtime::memory -- --test-threads=1
```

Дополнительно проверяется системный отказ выделения независимо от лимита:
тестовый аллокатор возвращает null последовательно на каждом выделении
вложенной записи. Все частичные резервы освобождаются, повторный перенос
успешен. Отказ роста строкового и типизированного буфера сохраняет исходные
данные и прежний резерв. Расширенные 15 тестов прошли под Miri с тем же
`strict-provenance`; [вывод](benchmarks/rush-managed-memory-miri-failures-2026-10-01.txt).
Подмена отказов локальна потоку теста и восстанавливается через `Drop`.

После подключения массива к ячейкам runtime прошли все тесты Rush (`--all-targets`),
Clippy, 575 тестов playground/WASM и 16 тестов памяти под Miri с
`strict-provenance`. [Вывод Miri](benchmarks/rush-managed-cells-miri-2026-10-01.txt)
включает системный отказ первой ячейки и отказ роста во время вызова функции,
после которого тот же экземпляр успешно выполняет следующие вызовы.
После перевода идентификаторов в тот же бюджет тест повторён с отказом
каждого из двух выделений: длины массивов остаются согласованными, старые
переменные доступны, следующий вызов успешен. Все 16 проверок памяти снова
прошли под Miri: [вывод](benchmarks/rush-managed-cell-ids-miri-2026-10-01.txt).

Следующий патч переводит также очередь освобождённых идентификаторов и список
свободных слотов на этот бюджет. Их ёмкость резервируется до публикации ячейки,
чтобы освобождение и повторное использование не выделяли память. Добавлены
проверки отказа каждого из четырёх выделений и переноса владения через `pop`.
После перевода очередей прошли 17 модульных тестов, 14 проверок времени жизни
ячеек и 5 проверок экземпляров. Все 17 проверок памяти после перевода очередей
также прошли под Miri с `strict-provenance`: [вывод](benchmarks/rush-managed-queues-miri-2026-10-01.txt).
Это проверяет обработку отказов, освобождение и перенос владения в этих тестах;
общий лимит памяти для остальных значений runtime по-прежнему не реализован.

Стек выполняемых импортов также переведён на `Slots` с общим резервом.
Отказ выделения происходит до изменения глубины и текущего модуля; тест
проверяет пустой стек, отсутствие записи в кеше и успешный повторный импорт
в том же экземпляре. Все 18 тестов памяти прошли Miri с `strict-provenance`:
[вывод](benchmarks/rush-module-stack-miri-2026-10-01.txt). Кеш экспортов модулей теперь также использует `Slots` с общим резервом.
Имена отсортированы: поиск двоичный, новая запись сдвигает хвост массива.
Отказ роста не меняет существующие записи; проверены доступ к старому модулю
и повторная загрузка нового в том же экземпляре. Все 19 тестов памяти прошли
Miri с `strict-provenance`: [вывод](benchmarks/rush-module-cache-miri-2026-10-01.txt).
Окружения и вложенные значения экспортов пока используют прежние выделения.
Место в кеше теперь резервируется до тела модуля, включая слоты для всех
активных родительских импортов. Отказ этого резерва не запускает инициализацию:
тест с хостовым счётчиком проверяет ноль вызовов при отказе и один после
успешной повторной загрузки. Ошибки самого тела модуля по-прежнему не откатывают
уже выполненные хостовые эффекты.

Массивы привязок окружений и захватов теперь используют `Slots` с тем же
резервом runtime. Поиск имени двоичный, добавление сохраняет сортировку.
Копирование окружения явно возвращает ошибку выделения; замена имеющейся
привязки не выделяет память. Расширение после деструктуризации резервирует
ёмкость до изменения исходного окружения. Ошибки сохраняют модуль и span.

Проверены отказы каждого выделения в вызове с деструктуризацией, вложенной
областью и замыканием: повторный вызов успешен, после удаления экземпляра
счётчик живых байтов равен нулю. Прошли тесты Rush, Clippy, 575 WASM-тестов
и 22 теста памяти под Miri: [вывод](benchmarks/rush-environments-miri-2026-10-01.txt).
Это пока учёт массивов привязок: `Rc`-обёртки, AST замыканий и вложенные `Value`
ещё выделяются прежним способом; общий публичный лимит остаётся незавершённым.

Дополнительные тесты с конечным бюджетом проверяют общий родительский захват,
отдельный резерв копии и атомарный отказ расширения окружения. Расширение
теперь резервирует только новые имена: замена существующих привязок работает
при полностью занятом бюджете. Возвращённое наружу замыкание удерживает резерв
захвата после удаления экземпляра; последний владелец освобождает его.
Прошли 25 модульных тестов, Clippy и прицельные проверки этих сценариев в Miri.

Разделяемые объекты окружений захватов также переведены с `Rc` на внутренний
`Shared`: одна учтённая аллокация включает счётчик владельцев, окружение и резерв.
Копирование ссылки не выделяет память, последний владелец освобождает объект
и резерв, включая случай паники деструктора. Указатель и число владельцев
передаются существующему сборщику циклов. Тип однопоточный, слабых ссылок нет.
Отказ выделения возвращается как ошибка окружения до публикации захвата.

Прошли тесты Rush, Clippy, 575 WASM-тестов и 27 проверок памяти под
[Miri](benchmarks/rush-shared-captures-miri-2026-10-01.txt) и
[AddressSanitizer](benchmarks/rush-shared-captures-asan-2026-10-01.txt).
Вложенные значения, объекты самих функций, AST и остальные `Rc` остаются
отдельными этапами; это ещё не общий лимит памяти.

Для вложенных импортов с возвращаемыми замыканиями проверен последовательный
отказ каждого управляемого выделения до первого успешного вызова. После каждого
отказа восстановлены модуль, глубина, стек загрузки и таблица ссылок; повторный
вызов успешен, после удаления экземпляра живой резерв равен нулю. Сценарий
прошёл обычный тест и [Miri](benchmarks/rush-nested-import-failures-miri-2026-10-01.txt).

Временный граф сборщика циклов переведён на общий резерв: узлы, рёбра,
очередь обхода, отметки достижимости, список освобождаемых ячеек и таблица
идентификаторов. Таблица использует открытое хеширование с заполнением не более
половины; пробы при коллизиях и перестройка учитываются в бюджете шагов.
Построение и анализ графа завершаются до изменения ячеек. Последовательные
отказы выделений на нескольких циклах проверяют сохранение живых значений,
освобождение временного резерва и успешную повторную сборку. Native-тесты Rush,
Clippy и 575 WASM-тестов прошли; тесты повторены без увеличения лимитов шагов.
Расширенный отказной сценарий прошёл [Miri](benchmarks/rush-gc-storage-miri-2026-10-01.txt).

Таблица сборщика отдельно проверена на ключах, коллидирующих при росте
16 → 32 → 64: записи сохраняются, повторное добавление не создаёт узлов,
поиск расходует шаги на каждую пробу и прекращается по отмене. Тест прошёл
[Miri](benchmarks/rush-gc-collisions-miri-2026-10-01.txt).

Массив стадий ленивой последовательности теперь разделяется через `Shared`
и использует общий резерв. Добавление `map`/`filter` создаёт новый массив до
замены старого; отказ массива или его разделяемой обёртки сохраняет исходную
цепочку. Сборщик циклов видит массив стадий отдельным узлом, а оценка
сохранённых данных учитывает его единожды. Прошли тесты Rush, Clippy,
575 WASM-тестов и [Miri для отказов копирования](benchmarks/rush-sequence-stages-miri-2026-10-01.txt).
Сами объекты `Sequence`, списки-источники и вложенные значения остаются
в прежнем хранилище; общий лимит памяти ещё не завершён.

Список-источник `iter(list)` переведён на `Buffer<Value>` с резервом массива
и разделяемого заголовка. Отказ любого выделения освобождает частичный буфер,
повторное создание успешно. Сборщик и оценка сохранённых данных используют
идентичность этого буфера. Прошли тесты Rush, Clippy, 575 WASM-тестов и
[Miri для отказов источника](benchmarks/rush-sequence-source-miri-2026-10-01.txt).
Вложенные `Value` внутри буфера остаются прежними: это не завершение общего
лимита. Не подключённые `Text`/`Record` и динамический лимит бюджета пока
компилируются только как тестовые прототипы; их базовые операции проверены.

Завершился длительный [Miri-прогон 14 тестов времени жизни ячеек](benchmarks/rush-shared-capture-cycles-miri-2026-10-01.txt)
для состояния с управляемыми захватами, до перевода графа сборщика и стадий
последовательностей. Все 14 прошли; этот результат не заменяет проверку
последующих изменений.

В тестовом прототипе `Record` устранено расхождение для повторяющихся ключей:
сортировка сохраняет исходный порядок через временные индексы, после чего
остаётся последнее определение ключа, как в текущем `BTreeMap` runtime.
Временный индекс и итоговые уникальные записи используют резерв. Проверены
пустая запись, дубликаты и отказ каждого из трёх выделений конструктора;
после отказа живой резерв равен нулю. Проверки прошли в обычном запуске,
Clippy и [Miri](benchmarks/rush-record-prototype-miri-2026-10-01.txt).
Прототип ещё не подключён вместо публичного `Value::Record`.

Граница публичного `Sequence::clone` проверена отдельным сценарием хоста:
две разные обёртки последовательности разделяют массив стадий и входят в цикл
через изменяемую ячейку. За 200 итераций создано 200 отслеживаемых ресурсов,
пик живых не превышает 64, в конце живых нет. Прошли все 15 тестов времени
жизни, Clippy и [AddressSanitizer для этого сценария](benchmarks/rush-host-sequence-clones-asan-2026-10-01.txt).
Это подтверждает учёт разделяемых стадий на публичной границе; строки,
записи и вложенные списки всё ещё требуют отдельного внутреннего представления.

### Проверки математических выражений в редакторе

Анализатор распознаёт размерности `vec2`/`vec3`/`vec4`, сохраняет известные типы
неизменяемых переменных и алиасов, учитывает области видимости и локальные
переопределения конструкторов. Векторная арифметика сохраняет размерность там,
где runtime однозначно определяет результат. Известные несовместимые операнды
и отсутствующие компоненты диагностируются до выполнения; неизвестные типы
остаются предметом runtime-проверки.

WASM передаёт поля известных векторов в метаданные bindings. В playground
проверен сценарий `let v = vec3(1,2,3); v.` → Ctrl+Space → выбор `z` → результат
`3`. Подсказки не добавляют скобки вызова. Отсутствующее имя поля в конце
исходника сохраняет метаданные, но не делает программу допустимой для запуска.

### Свидетельства для сквозных программ

- Записи: `record_summary` читает JSON в хосте, передаёт типизированные строки
  Rush, выполняет фильтрацию и группировку, сериализует результат обратно в JSON.
  Fixture и тесты проверяют суммы, порядок групп, исключение неактивных строк,
  Unicode, пустой ввод, неверные поля и очистку после ошибки исполнения.
  Агрегация использует `fold_by` с одним вызовом ключа на строку;
  для каждой группы хранится сумма. Режим JSON-массива буферизует вход;
  `--jsonl` читает через HostSequence с пределом физической строки 64 КиБ.
  Тест потока из 10000 строк проверяет точные суммы двух групп.
- Объекты приложения: `host_scene` создаёт, изменяет и удаляет точки хоста;
  результат геометрии экспортируется приложением.
- Разрешённый вход: `host_lines` читает выбранный хостом файл через `HostSequence`;
  закрытие при ошибке и отмене отдельно проверяется в `tests/host_sequences.rs`.

Примеры показывают API встраивания. Они не доказывают интеграцию с отдельным
пользовательским приложением или общий предел памяти процесса.
