# Forma: статическая проверка типов выражений (draft)

Дата: 2026-10-26. Ветка `language-improvements`, базовый коммит `ffa43a7`.
Это дизайн-документ; реализация не начата. Предлагаемые имена API и коды ниже
являются частью дизайна, а не описанием уже существующего поведения.

## Сводная таблица решений

| Вопрос | Решение |
| --- | --- |
| Основной принцип | Диагностика только при доказанной несовместимости; `Unknown` и отсутствующая схема подавляют вывод, а не порождают предупреждение |
| Стадия 1 | Локальный синтаксически направленный вывод; свойства и двусторонние привязки, аргументы чистых функций и событий, условия, операторы, `match`, юниты |
| Не входит | Hindley–Milner, пользовательские generics, междокументный вывод, вывод по значениям предпросмотра, исчерпываемость `match`, доказательство диапазонов чисел |
| Источники типов | `prop`/`state`/`event`, enum/struct, безопасные defaults, литералы, закрытая таблица сигнатур, схемы свойств и actions от хоста |
| Неопределённые значения | `Unknown` заразителен для проверки; `Any` также не является основанием для ошибки; неизвестные поля и внешние ссылки молчат |
| Место в pipeline | Общий анализатор вызывается из `lint_document`; старый `lint_document(source)` сохраняется, контекст добавляется отдельным API; `validate_contract` не расширяется |
| Диагностики | Аддитивные записи в существующем массиве `lint`: новые kebab-case коды, `severity: "error"`, UTF-16 `from`/`to`, ожидаемый и фактический типы |
| AST и offsets | Транспортный JSON AST не меняется; позиции выражений собираются во внутреннюю sidecar-таблицу при разборе |
| Главный gate | Ноль подтверждённых ложных срабатываний на 87-файловом корпусе и наборе known-good; обязательные mutation-тесты доказывают, что проверка не отключена фактически |

## 1. Текущее состояние и границы задачи

Сейчас статическая гарантия ограничена конкретными значениями контракта:
`validate_contract` берёт `definitions`, `values`, `enums` и вызывает
`matches_type` (`semantics.rs:468-552, 606-646`). Он не выводит тип AST-выражения
и не знает ожидаемого типа места использования. Поэтому объявленный
`state.name: String` и `width: state.name` могут пройти разбор, а несовместимость
обнаружится только при вычислении или в хосте.

Исходные возможности, на которые опирается дизайн:

- Парсер уже строит JSON AST выражений: ссылка `{"expr": …}`, литералы JSON,
  `interpolation`, `match`/`branches`, а под `expression` — `call`, `member`,
  `binary`, `unary`, `conditional` (`frontend.rs:566-845, 882-985`).
- Отдельного Rust-типа `Expr` и отдельной таблицы сигнатур нет. Имена функций
  перечислены в `is_pure_function` (`frontend.rs:365-441`), число аргументов и
  runtime-проверки — в `evaluate.rs:595-1481`. Статические сигнатуры нужно
  собрать в явный каталог и проверить его соответствие обоим местам.
- Типы объявлений представлены строками. `validate_type_name` и `matches_type`
  уже задают union `|`, `T?`, `List<T>`, `Map<T>`, `Record<String, V>`, enum,
  struct и примитивы (`semantics.rs:375-552`). Парсер хранит struct отдельно в
  `structs`, enum — в `enums` (`frontend.rs:1239-1298`).
- `propertyRanges` и `statementRanges` уже содержат UTF-16 offsets, но узлы
  выражений собственных позиций не содержат. Тест совместимости сравнивает AST
  87 файлов почти дословно (`tests/frontend.rs:4-31`), поэтому добавлять `start`
  в каждый expression node нельзя без отдельной миграции протокола.
- `lint_document` разбирает документ и возвращает массив предупреждений с
  `code`, `from`, `to`, `message` (`frontend.rs:2506-2690`). WASM операция `lint`
  просто сериализует этот результат (`packages/forma/wasm/src/lib.rs:63-101`),
  JS-адаптер экспортирует `lintDocument` (`packages/forma/src/language.js:4-7`).
- `Diagnostic {code, message, span}` и JS `Error` с additive `code`/`span`
  используются для неудачных операций, а не для списка линтов
  (`diagnostic.rs:1-63`, `packages/forma/wasm/src/lib.rs:15-25`). Эти два
  транспортных представления не следует смешивать.

Studio владеет компоновкой компонентов, runtime-данными и ссылками на модель
(`packages/forma/README.md:9-13`). В `tokenizer-forma` нет полного каталога типов
встроенных свойств и нет типов внешних `actions`. `scene.rs` описывает отдельное
renderer-подмножество и не является таким каталогом (`crates/tokenizer-forma/README.md:9-17`).
Следовательно, проверка `width` без дополнительного входа была бы угадыванием.

Отдельных AST-конструкций `show`/`hide` в полном frontend нет. Одноимённые
свойства, если их предоставляет хост, проверяются по внешней схеме как обычные
свойства. Структурные условия — `if`, `where`, условный оператор и guard —
проверяются непосредственно как `Bool`.

## 2. Область стадии 1

### 2.1 Что проверяем

1. **Значение свойства против ожидаемого типа.** Например, при схеме
   `width: Length` и `state.name: String` выражение `width: state.name` даёт
   `incompatible-binding`. Это относится к обычным `props`, свойствам ветвей
   группового `match`, defaults компонента и `forward`, если известны обе стороны.
2. **Двусторонняя привязка.** Для `value <-> state.name` проверяется совместимость
   типа свойства и типа пути. Поскольку значение читается и записывается, тип
   должен быть допустим в обоих направлениях; при `Unknown` проверка молчит.
3. **Аргументы чистых функций.** Проверяются типы аргументов всех имён из
   `is_pure_function`, включая overloads вроде `contains` и `slice`. Число
   аргументов остаётся ответственностью существующего parser/evaluator; новый
   проход не дублирует эти ошибки. Если сигнатура функции ещё не формализована,
   вся проверка вызова пропускается, а не заменяется приблизительной.
4. **Аргументы событий.** Локальные `eventDefinitions` дают ожидаемые типы для
   `events.name(...)`; схемы внешних `actions` может передать хост. Обработчики
   `state.*` без схемы не проверяются.
5. **Операторы и условия.** `if`, `where`, guard, `condition ? …`, `!`, `&&`, `||`
   требуют `Bool`; арифметика — `Number`; `+` допускает либо два `Number`, либо
   две `String`; диапазоны — два `Number`; сравнения следуют runtime-правилу
   «два числа или две строки». Равенство не ограничивается, поскольку runtime
   сравнивает JSON-значения структурно.
6. **`match` и union.** Паттерн, который не подходит ни к одной известной
   альтернативе subject, даёт `incompatible-match-pattern`. Guard проверяется
   как `Bool`. Каждое значение ветви проверяется против ожидаемого типа всего
   `match`; без внешнего ожидания типы ветвей объединяются. Проверки неполноты и
   новой достижимости ветвей нет: существующий `unreachable-branch` остаётся
   отдельным линтом.
7. **Юниты.** Литералы `px`, `%`, `rem`, `em`, `vw`, `vh`, `ch`, `fr`, `ms`, `s`,
   `deg`, `rad`, `turn` получают соответственно `Length`, `Duration`, `Angle`.
   Передача `1px` в `Duration` или `100ms` в `Length` — ошибка. Юнит не считается
   `Number`: арифметика над ним отклоняется, потому что evaluator не выполняет
   неявного числового преобразования (`LANGUAGE.md:142-146`).
8. **Все expression-контексты документа.** Обход включает `nodes`, `defaults`,
   `lets`, `stateDefinitions.default`, `matches`, `styles`, `tokens`, `i18n`,
   `slots`/`slotArgs`, `shortcuts.args`, `overrides`, `states`, `entries`, а также
   `if`/`for`/`match` и аргументы обработчиков. Отсутствие внешнего ожидаемого
   типа отключает только проверку результата, но не вложенные вызовы и условия.
   `for key` имеет ожидаемый `String | Number`; заведомо коллекционный ключ даёт
   `incompatible-binding`. Части интерполяции должны быть скалярами, принимаемыми
   `evaluate::text`; известный список/объект даёт `incompatible-operand`, а
   `Unknown` молчит. Пути `use`/`#[design]` остаются строковыми декларациями и не
   получают дополнительной семантики.

### 2.2 Что сознательно не проверяем

- Общий вывод типов, унификацию, let-polymorphism и пользовательские generics.
  Параметрические записи вида `List<T>` разбираются, но это не объявление
  обобщённого типа пользователем.
- Согласование типов между независимо загружаемыми документами. Хост передаёт уже
  разрешённые контракты; анализатор не ходит в файловую систему и не строит graph
  модулей.
- Исчерпываемость `match`, сужение union после guard, анализ достижимости и
  постоянное выполнение ветвей.
- Проверку конкретных preview/runtime-значений, ограничения `#[range]` и
  `#[pattern]`, уникальность ключей и существование ресурсов `Asset`.
- Доказательство неотрицательности произвольного `Number` для `Length`, целости
  произвольного `Number` для `Int`, конечность вычисленного результата и ошибки
  вроде деления на ноль. Это value analysis, а не типовая стадия 1.
- Полный контроль неизвестных свойств. Если member access не имеет схемы,
  результат — `Unknown`, даже если другой проход мог бы сообщить об опечатке.

## 3. Модель типов и вывода

### 3.1 Внутреннее представление

Нужен отдельный внутренний `Type`, а не повторный разбор строки на каждом узле:

```text
Unknown | Any | Null | Bool | Number | Int | String | Asset | Color
Length | Duration | Angle | List(Type) | Map(Type) | Record(Type)
Enum(name) | Struct(name) | Union(types)
```

`Boolean` нормализуется в `Bool`, `Float` — в `Number`; голые `List` и `Map`
получают элемент `Any`, `Object` представляется как объект с неизвестными
значениями. `T?` нормализуется в `Union(T, Null)`. Для пустого списка допустим
внутренний элемент `Unknown`: он совместим с любым `List<T>` и не создаёт ошибок.
Для числовых литералов сохраняются признаки «целое» и, только для диагностики
самого литерала, знак; общего range analysis это не начинает.

Enum и struct остаются именованными ссылками в окружение документа. Структурные
поля используются при member access. Дополнительные runtime-поля struct не
становятся основанием для утверждений о `Record<String, V>`.

### 3.2 Откуда берутся типы

- `propDefinitions`, `stateDefinitions`, `eventDefinitions` — основной,
  стабильный источник. Default проверяется против объявленного типа, но не
  заменяет его более узким литеральным типом.
- `enums`, `structs` и `_structConstraints` разделяются: constraints не меняют
  тип. Enum-ссылка `Tone.Accent` распознаётся только по объявленному enum.
- Локальные `let`, `tokens` и `i18n` можно выводить по defaults, если зависимость
  не циклична. Цикл или ссылка на ещё не вычислимый inferred default даёт
  `Unknown`; глобального fixed point нет.
- **Legacy default внешне переопределяемого prop не является стабильным типом.**
  Например, `text: 1;` без `prop text: Number` не доказывает, что хост никогда не
  передаст строку. Такие defaults можно проверять в месте объявления, но нельзя
  использовать как несомненный тип чтения `props.text`. Это важная защита от
  ложных срабатываний.
- Литералы JSON дают `String`, `Bool`, `Null`, `Int`/`Number`; списки и объекты
  выводятся по элементам. Цвет `#…` и юниты, которые парсер хранит как `expr`,
  классифицируются до неизвестной host-ссылки по строгой лексической форме.
- Таблица функций даёт аргументы и результат. Для `first(List<T>)` допустимо
  закрытое сопоставление `T` с элементом конкретного списка и результат `T|Null`;
  это правило одной встроенной сигнатуры, а не generics языка. Если результат
  зависит от динамического ключа и не выразим точно, возвращается `Unknown`.
- `TypeContext` хоста даёт типы встроенных свойств, дочерних компонентов и
  `actions`. Отсутствующая запись означает `Unknown`, а не `Any`-совместимость с
  последующей ошибкой и не диагностику «схема не найдена».

`viewport`, `base`, динамические `locals` и внешние `tokens` без объявления тоже
могут отсутствовать в контексте. Их использование остаётся законным и молчит.

### 3.3 Совместимость без ложных срабатываний

Центральная операция — `assignable(actual, expected) -> Yes | No | Unknown`,
а не исполнение `matches_type` на AST. `No` разрешено только при полностью
известном доказательстве несовместимости.

- `Unknown` в любой значимой позиции даёт `Unknown`; ожидаемый `Any` принимает
  всё, фактический `Any` даёт `Unknown`. Ни один из этих случаев не порождает
  диагностику.
- Для фактического union каждая альтернатива обязана быть допустимой: например,
  `String | Int` нельзя передать в `Number` из-за известной альтернативы `String`.
  Если одна альтернатива `Unknown`, весь результат проверки — `Unknown`.
  Для ожидаемого union достаточно одной подходящей известной альтернативы.
- `Int` допустим как `Number`; произвольный `Number` не доказывает `Int`.
  `Number` допустим как `Length` и `Angle`: неотрицательность — отдельное
  динамическое ограничение, иначе обычный `width: clamp(...)` был бы ложно
  отклонён. `Length`/`Angle` не допускаются как `Number`, поскольку включают
  строковые юниты. `Duration` числом не является.
- `Asset` и `String` взаимно допустимы, как в `matches_type`; `Color` — отдельный
  формат, а не произвольная `String`. Проверка должна повторять именно эти
  решения `matches_type`, а не вводить новые неявные преобразования.
- `List<T>`, `Map<T>`, `Record<V>` проверяются рекурсивно по элементам/значениям.
  `Record` не требует generics по ключу: ключ уже зафиксирован как `String`.
- Overload принимается, если хотя бы одна полная сигнатура доказанно подходит.
  Если из-за `Unknown` нельзя выбрать overload, ошибки нет. Нельзя отклонять
  вызов только потому, что часть overloads не подошла.

Ошибка означает несовместимость объявленных типов, а не обещание, что конкретный
запуск обязательно упадёт. Анализ не использует preview-значения для «оправдания»
несовместимого выражения.

### 3.4 Локальные правила вывода

- `?.` добавляет `Null`; `??` убирает `Null` из левого известного типа и объединяет
  результат с правым. `coalesce` действует аналогично по аргументам.
- Условный оператор и `match` без внешнего ожидания объединяют типы ветвей. При
  внешнем ожидании каждая ветвь проверяется отдельно — так диагностика указывает
  на конкретную ветвь.
- `length` строки/списка и числовые счётчики дают `Int`; известный member struct
  даёт тип поля; `List<T>[…]` даёт `T`; `Map<T>`/`Record<T>` — `T`. Динамический
  объект без схемы даёт `Unknown`.
- `for item in collection` получает `T` только при известном `List<T>`; индекс —
  `Int`. При другом известном типе коллекции допустима `incompatible-binding`
  контекста `for`, при неизвестном — `Unknown`. Тело анализируется в обоих случаях.
- После уже выданной ошибки результат узла заменяется на `Unknown`, чтобы не
  порождать каскад производных сообщений. Обход и порядок диагностик — по исходным
  позициям, не по порядку ключей JSON.

## 4. Контекст внешних типов

Предлагается не зашивать неполный список свойств из `scene.rs` в новый анализатор.
В Rust появляется `TypeContext`, а через WASM — необязательный JSON `context` с
эквивалентной информацией: типы свойств по node type (включая общие свойства),
разрешённые контракты дочерних компонентов и сигнатуры `actions`.

Точная JSON-схема утверждается на стадии 0 вместе с потребителем Studio. Инвариант
API важнее её конкретных имён:

- `lintDocument(source)` продолжает работать и означает пустой внешний контекст;
- `lintDocument(source, context)` позволяет Studio передать схему;
- старый Rust `lint_document(source)` сохраняется как wrapper с пустым контекстом;
- отсутствие типа свойства отключает только проверку этого места, а не остальной
  анализ документа;
- наследование и поиск `use` разрешает хост, анализатор получает уже готовый тип.

Так `width: state.name` становится проверяемым при переданном
`width: Length`, но отсутствие каталога не превращается в ложную ошибку.

## 5. Диагностики и место в pipeline

### 5.1 Коды и полезная нагрузка

Новые коды, все в kebab-case:

| Код | Место |
| --- | --- |
| `incompatible-binding` | свойство, `forward`, двусторонняя привязка, default, коллекция `for` |
| `incompatible-argument` | аргумент чистой функции или типизированного события/action |
| `incompatible-condition` | `if`, `where`, guard, условие тернарного оператора |
| `incompatible-operand` | унарный/бинарный оператор |
| `incompatible-match-pattern` | паттерн не подходит ни к одной известной альтернативе subject |
| `incompatible-match-branch` | результат ветви не соответствует ожидаемому типу всего выражения |

Запись добавляется в существующий результат `lint` и содержит как минимум
`code`, `message`, `from`, `to`, `severity: "error"`, `expected`, `actual`.
Допустимы additive `name`/`context`, например имя функции и индекс аргумента.
Старые линты без `severity` сохраняют прежний смысл предупреждений. Сообщения —
по-русски; `expected`/`actual` — канонические строки типов, пригодные для тестов,
но не заменяющие человекочитаемое сообщение.

`from`/`to` — UTF-16 offsets всего виновного подвыражения: аргумента, паттерна,
значения ветви или пути привязки. Если точной позиции нет, используется уже
существующий `propertyRanges`/`statementRanges`; искусственный offset `0`
запрещён. Отсутствие диапазона лучше выдуманного, но для стадии 1 точные ranges
аргументов являются приёмочным критерием.

Эти записи не проходят через `Diagnostic::to_json`, потому что `lint` возвращает
успешный результат со списком. Ошибка разбора по-прежнему приходит как JS `Error`
с `code` и одиночным `span`; её контракт не меняется.

### 5.2 Sidecar-позиции, не новая схема AST

Внутренний разбор для анализа должен вернуть `(document, expressionSpans)`:
ключ — стабильный путь к expression node в документе, значение — UTF-16 range.
Парсер фиксирует начало и конец на входе/выходе `expression`, включая вложенные
аргументы и паттерны. Для `${…}` базовый offset подстроки добавляется к offsets
вложенного разбора. Пути привязок и аргументы событий получают ranges так же.

Публичные `parse`/`parse_expression` по-прежнему возвращают только прежний JSON.
Sidecar не сериализуется в WASM AST и не участвует в `evaluate::equal`.
Это сохраняет 87-файловый корпус и Studio-совместимость без «скрытого» режима
с двумя разными грамматиками: режимы делят один parser, отличие только в записи
метаданных.

### 5.3 Почему `lint`, а не `validate_contract`

`validate_contract` проверяет уже материализованные JSON-значения, required и
constraints и используется независимо от исходника. Расширение его AST-выводом
смешало бы два контракта, потребовало бы `TypeContext` в runtime-вызовах и не
дало бы естественного способа вернуть несколько диагностик. Он остаётся без
изменений; старый код `type-mismatch` также остаётся.

Статический проход размещается после успешного `parse` внутри общего lint
pipeline. Синтаксически невалидный документ по-прежнему возвращает одну ошибку
разбора и не запускает вывод. Статические несовместимости не делают `parse` или
`evaluate` неуспешными и не меняют runtime. Новая отдельная WASM-операция не
нужна: существующая `lint` уже передаёт массив и JS `Error` только для сбоя
самой операции.

## 6. План по стадиям и критерии

### Стадия 0. Характеризация, без новых диагностик

1. Составить каталог всех имён из `is_pure_function`: arity, допустимые overloads,
   результат, отклонения вида «динамический результат — `Unknown`». Тест должен
   упасть при имени из parser whitelist, отсутствующем в каталоге.
2. Зафиксировать с Studio `TypeContext` и происхождение типов общих свойств.
   Не копировать вручную неполный каталог из `scene.rs`.
3. Добавить sidecar ranges без изменения публичного AST. Критерий: существующий
   87-файловый тест проходит без изменения fixture; тесты с ASCII, кириллицей и
   emoji подтверждают UTF-16 ranges вложенного аргумента и интерполяции.
4. Снять baseline существующих линтов на корпусе, чтобы новые коды отличались от
   старых `unused-*`, `duplicate-shortcut`, `unreachable-branch`.

### Стадия 1. Ядро анализа в shadow mode

1. Ввести `Type`, разбор объявлений, `assignable`, вывод литералов/ссылок/
   операторов и таблицу функций. Публичный `lint` пока не включает новые записи.
2. Подключить defaults, условия, чистые функции, локальные события, `match`, юниты,
   затем свойства и двусторонние привязки через `TypeContext`.
3. Unit-тесты обязаны содержать как обнаруживаемые ошибки, так и молчание:
   - `String -> Length`, `Number -> String`, `1px -> Duration`, неверный guard;
   - `trim(Number)`, неверный аргумент `events.open`, несовместимые ветки;
   - `String | Int -> Number`, enum subject с паттерном другого enum;
   - `Unknown`, `Any`, отсутствующая схема, динамический member, legacy default,
     неизвестный action — ни одной новой диагностики;
   - `Number -> Length`, `Int -> Number`, `T?` после `??`, empty list,
     совместимый union и каждый поддерживаемый юнит — ни одной ошибки;
   - `List<String> -> List<Number>` и `List<T>` с `Unknown` различаются.
4. Каждый новый код проверяется на стабильность, message, `expected`/`actual` и
   точный UTF-16 range. Проверяется отсутствие каскадных производных ошибок.
5. Mutation-тесты: для каждого семейства проверок known-good источник сначала
   молчит, затем минимальная замена типа даёт ровно ожидаемый код. Это отсекает
   «нулевой FP» ценой анализатора, который ничего не проверяет.

### Стадия 2. Корпусная приёмка и WASM/JS-адаптеры

1. Прогнать shadow-анализ всех 87 источников из `forma-corpus.json` с пустым
   контекстом и отдельно с production-контекстом Studio. Сохранить отчёт: файл,
   код, range, expected/actual, решение reviewer и воспроизведение для true positive.
2. Каждое сообщение классифицируется как `true-positive`, `false-positive` или
   `unresolved`. Критерий включения: `false-positive = 0` и `unresolved = 0`.
   Файл, который только парсится, не объявляется автоматически known-good: при
   споре находится runtime/contract reproduction либо правило ослабляется.
3. Дополнительно прогнать known-good набор из тестов `packages/forma` и примеров
   `LANGUAGE.md`. Покрытие записать числами: сколько expression contexts проверено,
   сколько пропущено из-за `Unknown`, сколько срабатываний дают mutations.
   Нулевые срабатывания на корпусе без этих чисел не считаются достаточным доказательством.
4. Подключить необязательный `context` в `operation_json("lint")` и JS wrapper.
   Старые вызовы без контекста остаются source-compatible; additive поля новых
   записей проверяются через публичный JS API.

### Стадия 3. Включение и регрессионные гейты

1. Включить новые записи в общий `lint_document` только после нулевого FP-gate.
2. Обновить `packages/forma/LANGUAGE.md`: область проверок, `Unknown`, внешний
   контекст, коды, отличие статических `incompatible-*` от runtime `type-mismatch`.
3. Обязательные команды:
   - `~/.cargo/bin/cargo test -p themoretheless-tokenizer-forma`;
   - `npm test` в `packages/forma`: все существующие 24 теста плюс новые adapter/
     diagnostics-тесты; само число 24 после добавления тестов не является целью;
   - отдельный corpus-тест: 87 AST не изменились, а новые диагностики соответствуют
     reviewed baseline без единого неподтверждённого сообщения.
4. Проверить WASM integration на ошибку parse и на успешный массив lint: первый
   сохраняет JS `Error.code/span`, второй содержит UTF-16 `from/to` и `severity`.
5. Любое последующее усиление правила повторяет shadow-прогон и FP-gate. Ослабление
   сигнатуры до `Unknown` допустимо как hotfix без изменения runtime.

## 7. Риски и честные границы

### 7.1 Ложные срабатывания — главный блокер

Главные источники: отсутствующие host-схемы, переопределяемые legacy defaults,
слишком строгое число/`Length`, union/overloads и неточное воспроизведение
полиморфных функций. Меры уже встроены в модель: `Unknown`, запрет вывода типа
внешне переопределяемого prop, `Number -> Length`, проверка полного overload,
пропуск неформализованной функции.

Ноль FP измеряется не отсутствием сообщений вообще, а ручной классификацией всех
сообщений на заранее зафиксированном корпусе плюс mutations. Нельзя называть
каждое несовпадение «ошибкой корпуса» без воспроизведения. При сомнении правило
считается неготовым и переводится в `Unknown`.

### 7.2 Каталог функций разойдётся с evaluator

Сегодня имена, arity и поведение находятся в разных местах. Статическая таблица
может стать третьим источником истины. Минимум — тест полного покрытия whitelist
и по одному runtime/static conformance-кейсу на overload. Предпочтительно parser
whitelist берёт имена из того же каталога; runtime dispatch при этом не
переписывается в рамках первой стадии.

### 7.3 Юниты и `expr` неоднозначны

Цвет, enum, размер и обычная host-ссылка могут иметь одинаковую JSON-оболочку.
Классификация должна быть лексически строгой и использовать объявления enum;
неизвестная форма остаётся ссылкой/`Unknown`. Особые значения раскладки (`*`,
`2*`, `auto`, `content`, `-`) не получают самодельный числовой тип: их смысл
должен задавать внешний property schema, иначе проверка пропускается.

### 7.4 Совместимость протокола

Новые поля в expression AST сломали бы точный corpus и потребителей Studio.
Sidecar исключает это. Добавление записей в `lint` тоже наблюдаемо: потребители,
которые считают каждую запись warning, должны научиться читать `severity` до
включения типовых ошибок в Studio. Rust/WASM ошибки операций не меняются.

### 7.5 Проверка будет неполной

Пустой внешний контекст не поймает `width: state.name`; `Any`, host-значения и
динамические ключи снижают покрытие; отсутствует исчерпываемость `match`. Это
осознанная цена no-false-positives, а не скрытое обещание полной типобезопасности.
Метрика покрытия обязательна, чтобы не выдавать молчание за доказательство
корректности.

## 8. Открытые вопросы

1. **Владелец каталога встроенных свойств.** Рекомендация драфта — Studio/
   component linker поставляет `TypeContext`; альтернатива — завести в
   `tokenizer-forma` версионируемый полный каталог примитивов. До выбора нельзя
   обещать проверку `width` при пустом контексте.
2. **Представление severity в Studio.** Предлагается `severity: "error"` только у
   новых записей и сохранение старых линтов как warnings. Если Studio пока не
   различает severity, сначала нужен adapter, а не изменение смысла всех записей.
3. **Степень вывода для legacy defaults.** Драфт выбирает самый строгий вариант
   против FP: не использовать переопределяемый default как тип чтения. Если
   продукт объявит такие значения sealed, отдельный флаг контекста сможет включить
   более сильный вывод без изменения базового правила.
4. **Будущий strict-режим union.** Стадия 1 считает известную несовместимую
   альтернативу фактического union ошибкой. Более мягкий режим «ошибка только
   если ни одна альтернатива не подходит» менее полезен и не рекомендуется; менять
   это решение следует только по измеренным corpus-данным, не в середине стадии.
