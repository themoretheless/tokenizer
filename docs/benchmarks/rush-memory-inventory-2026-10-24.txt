=====================================================================
2. Allocation paths NOT covered by any limit or counter
=====================================================================
- AST nodes after parse (Box<Expr>, Vec<Stmt>, Vec<Parameter>, MatchArm, InterpolationPart):
  ast.rs:39-207; parser allocates freely, bounded only by max_tokens count (lexer.rs:29), not bytes.
  Parse output (AST + tokens) is retained for the whole Program lifetime and never enters
  retained_usage() (instance.rs:260-383 covers only runtime Values and environments).
- Lexer token vector itself (LexToken = kind+span, ~16 B/token): fullkit.rs:62-71.
- Transient evaluation buffers: eager sequence materialization peaks (see §3),
  temporary Vec in arithmetic/concat (expr.rs:583 builds a new String per `+`).
- Closure captures / environments: counted by Budget (usize::MAX) but not by any enforced limit.
- Host callbacks: native allocations inside host calls are explicitly unbounded
  (types.rs:843 "do not bound heap memory or blocking host calls",
   instance.rs:259 "host-owned allocations are opaque");
  host results are checked only after allocation (runtime.rs:760-803).
- Process RSS / allocator retention: not tracked (MallocLargeCache policy, docs/rush-performance.md:280-340).

1000 iterations: 2.54 MB cumulatively allocated for a 1000-byte live result (~2541x).
10000 iterations: 250.1 MB cumulative for a 10 KB result (~25000x) — quadratic, as expected.
max_string_bytes (expr.rs:583) caps only the CURRENT string length; cumulative work
and allocator churn are invisible to every existing limit. Peak stays small (~60 KB
at 10k iterations) because each intermediate string is freed on the next iteration,
so even a peak-heap counter would miss the quadratic cost; only cumulative accounting
(or the steps budget) sees it.
